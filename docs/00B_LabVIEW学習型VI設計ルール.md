# 00B. 学びながら作るLabVIEW VI設計ルール

**制定日：2026-07-18**

本書は、本リポジトリ内で作成・改訂するすべてのLabVIEW VIについて、配置・配線手順だけでなく、機能要求をデータモデル、処理アルゴリズムおよびLabVIEWの構造へ落とし込む理由を説明するための共通ルールである。

[00A_LabVIEW実装資料の記述ルール.md](./00A_LabVIEW実装資料の記述ルール.md)が「第三者が画面を見ながら同じVIを再現できること」を目的とするのに対し、本書は「読者が設計理由を理解し、次のVIを自力で設計できること」を目的とする。

```text
00A：どの関数を、どこへ配置し、どの端子へ配線するか
00B：なぜそのデータモデル、アルゴリズム、Case、Loop、Shift Registerが必要か
```

両方を満たして初めて、実装手順を完成扱いとする。

---

## 1. 適用範囲

本ルールはDLLを使用するかどうかに関係なく、次のすべてへ適用する。

- DLL Wrapper
- Builder
- Parser
- 数値・文字列・配列変換VI
- ファイル保存VI
- 機器制御VI
- 状態監視VI
- 並列処理VI
- Cleanup VI
- Public API VI
- PoC VI
- TestStandから呼び出すVI

DLL WrapperではAPI仕様が処理の根拠になりやすいが、DLLを呼ばないVIでは設計者がデータの意味と処理手順を組み立てる必要がある。そのため、Builder、Parser、状態管理、ファイル保存および並列処理では本ルールを特に重視する。

---

## 2. 機能要求からLabVIEW構造までの翻訳順

VIを説明するときは、いきなりCase StructureやForループを配置しない。次の順番で設計理由を示す。

```text
欲しい機能
  ↓
入力データの実体
  ↓
出力データモデル
  ↓
守る必要がある前提条件・異常条件
  ↓
処理アルゴリズム
  ↓
必要な状態・繰り返し・分岐
  ↓
LabVIEW構造の選定
  ↓
関数配置・配線
  ↓
単体テスト
```

悪い説明：

```text
Forループを配置し、Case Structureを中へ置く。
```

良い説明：

```text
Channel Listには同じ形式のチャンネル設定が複数格納されている。
各チャンネルへ同じ変換処理を1回ずつ適用する必要がある。
したがって、Channel Listの要素数だけ反復するForループを使用する。
各反復で前段エラーが発生している場合は変換を止め、累積配列を保持する必要があるため、
ループ内へerror statusをselectorとするCase Structureを配置する。
```

## 3. VI作成手順の学習型標準構成

新規VIまたは大幅改訂するVIの資料は、原則として次の順番にする。

```text
0. 実現したい機能とVIの責務
1. 入力データの実体
2. 出力データモデル
3. 前提条件・異常条件
4. 処理アルゴリズム
5. LabVIEW構造の選定理由
6. 入出力
7. 配置する関数およびSubVI等
8. 配線順
9. 単体テスト
```

既存資料の`0. 目的と処理概要`へまとめる場合でも、少なくとも次を小見出しまたは表で含める。

```text
・何を実現するか
・入力データは内部でどのように並んでいるか
・出力をどのクラスタまたは配列で表すか
・処理をどの単位へ分解するか
・なぜCase、For、While、Shift Register等が必要か
```

単純な1入力1出力の変換VIでは節を統合してよい。ただし、構造を使用する理由を省略してよいという意味ではない。

## 4. 入力データの実体を書く

### 4.1 端子の型だけで終わらせない

`U8一次元配列`、`クラスタ`、`String`等の型だけでは、内部構造を理解できない場合がある。

例えば連続する測定Packetを持つU8配列なら、次のように見取り図を書く。

```text
Raw Buffer U8[]
├─ Packet 0
│  ├─ Channel 0 : 4byte
│  ├─ Channel 1 : 4byte
│  ├─ Flag      : 4byte
│  └─ Timestamp : 8byte
├─ Packet 1
│  └─ 同じ構造
└─ ...
```

### 4.2 配列、レコード、階層を示す

次を明記する。

- 1要素が何を表すか。
- 1レコードのサイズ。
- レコード数が固定か可変か。
- レコード内のフィールド順。
- 配列が入れ子の場合の階層。
- バイトオーダー。
- 符号の解釈。
- 長さを決める別入力。

### 4.3 データの所有者を示す

必要に応じて、データを誰が生成し、誰が解放するかを書く。

```text
機器が生成
DLLが一時保持
LabVIEWがコピー
LabVIEWが解析
CleanupでDLL側バッファを解放
```

---

## 5. 出力データモデルを書く

### 5.1 なぜそのtypedefが必要か

typedef一覧を示すだけでなく、Rawデータをどの意味単位へ変換するための型なのかを書く。

```text
U8[4]
  ↓ 数値変換
Raw U32
  ↓ 符号解釈
Value
  ↓ ScaleとOffset
Engineering Value
  ↓ Name、Address、Unitを付加
Channel Valueクラスタ
```

### 5.2 単体、配列、クラスタの関係を示す

```text
Channel Value.ctl = 1チャンネル分
Channel Values    = Channel Value.ctl一次元配列
Packet.ctl        = Channel Values + Flag + Timestamp
Packets           = Packet.ctl一次元配列
```

この関係を示すことで、Forループの自動指標付け出力が単体クラスタから配列を生成する理由を説明できる。

---

## 6. 前提条件と異常条件を書く

本処理へ入る前に成立していなければならない条件を列挙する。

例：

```text
・前段error in.statusがFalse
・Channel Count >= 1
・Data Count >= 0
・Raw Bufferの実サイズ >= 解析に必要なサイズ
・File Referenceが有効
・機器状態がアイドル
```

各条件について、次を説明する。

1. なぜ必要か。
2. 条件を破ると何が起きるか。
3. どのCase Structureで止めるか。
4. どの安全出力を返すか。
5. どのerror codeとsourceを返すか。

Case Structureが多段になる場合は、複雑さを増やすためではなく、前提条件を一段ずつ保証するためであることを書く。

---

## 7. 処理アルゴリズムを書く

### 7.1 LabVIEW関数名を使わない擬似コードを先に書く

配置手順の前に、欲しい機能を一般的な処理へ分解する。

```text
for each Packet
    for each Channel
        対象の4byteを切り出す
        数値へ変換する
        符号を解釈する
        工学値へ変換する
        Channel Valueを作る
    end

    Flagを取得する
    Timestampを取得する
    Packetを作る
end
```

この段階では`Array Subset`や`Bundle By Name`等の操作名を無理に入れない。まず機能ロジックが正しいか確認する。

### 7.2 計算式の意味を書く

式だけでなく、なぜその式になるかを書く。

```text
Packet Size = ChNum × 4 + 12
```

だけでは不十分。

```text
各Channelはログ上で4byte固定である。
全Channel分はChNum × 4byteとなる。
その後ろへFlag 4byteとTimestamp 8byteが続く。
したがってPacket Size = ChNum × 4 + 4 + 8 = ChNum × 4 + 12となる。
```

### 7.3 オフセット式を図と対応させる

```text
Packet Start    = Packet Index × Packet Size
Channel Start   = Packet Start + Channel Index × 4
Flag Start      = Packet Start + ChNum × 4
Timestamp Start = Flag Start + 4
```

各式がデータ見取り図のどの位置を示しているか説明する。

## 8. LabVIEW構造の選定理由を書く

### 8.1 機能ロジックと構造の対応

| 必要なロジック | LabVIEW構造 | 選定理由 |
|---|---|---|
| 条件によって処理を変える | Case Structure | 条件ごとに実行経路と安全出力を明示できる |
| 要素数が決まった配列を1件ずつ処理する | Forループ | 同じ処理を有限回反復できる |
| 停止条件が成立するまで処理する | Whileループ | 反復回数ではなく状態で終了できる |
| 前回までの値を次の反復で使う | Shift Register | 累積値、状態、errorを反復間で保持できる |
| 配列の指定位置を読む | Index Array / Array Subset | 単一要素または連続範囲を取り出せる |
| 配列の指定位置を更新する | Replace Array Subset | 既存配列を保持しながら一部を書き換えられる |
| 同じ型の出力を反復ごとに集める | 自動指標付け出力 | 単体出力から一次元配列を自動生成できる |
| 複数フィールドを意味単位へまとめる | Cluster / typedef | データの意味と型を固定できる |
| OpenからCloseまで資源を保持する | Refnum + Shift Register / State | ファイルやセッションの生存期間を管理できる |
| 複数処理の順序を保証する | error clusterの直列配線 | データフロー上の実行順を明確にできる |

### 8.2 構造ごとに説明する内容

#### Case Structure

- selectorは何か。
- True／Falseまたは各値が何を意味するか。
- なぜ分岐が必要か。
- 各ケースで何を出力するか。
- 分岐を1個へまとめず、多段に分ける理由。

#### Forループ

- 1反復で何を処理するか。
- 反復回数を何が決めるか。
- N端子を接続するか。
- 自動指標付けを有効または無効にする理由。
- ループ外とループ内で型がどう変わるか。

#### Whileループ

- 継続条件と停止条件。
- 最大待ち時間またはタイムアウト。
- Waitを入れる理由。
- 停止後に必要なCleanup。

#### Shift Register

- 初期値。
- 前回値。
- 今回更新値。
- 最終出力。
- Falseケース等で現在値を保持する理由。

### 8.3 代替案を採用しない理由を書く

重要な構造選定では、候補と不採用理由も短く記載する。

例：

```text
候補A：16個のレコード解析回路を横に複製する
不採用理由：同じ処理が重複し、フィールド追加時に16か所を修正する必要がある。

採用：Forループで1レコード分の解析回路を16回使用する
理由：処理を1か所に保ち、レコード数と開始位置だけを変えられる。
```

## 9. DLLを呼ばないVIで重点的に説明すること

### 9.1 Builder

```text
意味付き設定値
  ↓
DLLまたはファイル仕様で定められた順番へ変換
  ↓
Raw U8配列
```

説明事項：

- なぜ固定長配列を最初に作るか。
- 各フィールドの書込位置。
- なぜShift Registerで更新済み配列を保持するか。
- なぜReplace Array Subsetを直列にするか。

### 9.2 Parser

```text
Raw U8配列
  ↓
レコードまたはPacketへ分割
  ↓
数値へ変換
  ↓
意味付きクラスタへ変換
```

説明事項：

- Parserが必要な理由。
- レコード境界とオフセット。
- 外側Loopと内側Loopの処理単位。
- サイズ検証が必要な理由。
- 符号、Endian、Scale、Offsetの順番。

### 9.3 ファイル保存

説明事項：

- 保存対象の正本はRawか解析済み値か。
- Open、Append、Flush、Closeの責務。
- File Referenceをどこで保持するか。
- 測定中エラーでもCloseを試みる理由。
- 同じデータを二重保存しない条件。

### 9.4 状態管理・並列処理

説明事項：

- 状態一覧と遷移条件。
- 並列処理間で共有する値。
- Queue、Notifier、User Event等を選ぶ理由。
- 停止メッセージとTimeout。
- デッドロックや無限待ちを防ぐ設計。

## 10. 単体テストを設計ロジックと対応させる

単体テストは配線が切れていないことだけでなく、設計時の前提とアルゴリズムを検証する。

| 設計上の確認対象 | テスト例 |
|---|---|
| レコード境界 | 隣接フィールドへ異なる値を入れる |
| Endian | 同じ数値をLittle／Bigの両方で確認する |
| 符号 | `0xFFFFFFFE`をunsignedとsignedで比較する |
| Bufferサイズ | 期待値と同じ、1byte不足、余剰ありを確認する |
| Loop回数 | 0件、1件、複数件を確認する |
| Shift Register | 前半で検出した値が後半反復でも保持されることを確認する |
| Case分岐 | selectorをTrue／Falseへ変え、両ケースを実行する |
| Cleanup | 前段エラーありでもClose／Releaseが試行されることを確認する |

各テストには次を記載する。

```text
この入力を選ぶ理由
  ↓
通過するCaseまたはLoop
  ↓
期待する中間値
  ↓
期待する最終出力
```

## 11. 学習型説明の記載例

### 11.1 実現したい機能

```text
連続したRaw BufferからDataNum個のPacketを解析し、Packet配列へ変換する。
```

### 11.2 データの実体

```text
Raw Buffer
  = Packet 0 + Packet 1 + ...

Packet
  = Channel Data × ChNum + Flag + Timestamp
```

### 11.3 必要なアルゴリズム

```text
入力条件を確認する
必要バイト数を計算する
Raw Bufferが十分か確認する
Packetごとに処理する
各Packet内でChannelごとに処理する
FlagとTimestampを取得する
Packet配列へまとめる
```

### 11.4 構造の選定理由

| 構造 | 理由 |
|---|---|
| 外側error Case | 前段エラー時に解析を開始しないため |
| Input Valid Case | ChNumとDataNumの前提を保証するため |
| Buffer Size Case | 配列範囲外の読出しを防ぐため |
| 外側Forループ | DataNum個のPacketを処理するため |
| 内側Forループ | ChNum個のChannelへ同じ変換を行うため |
| error Shift Register | 途中エラーを後続反復へ引き継ぐため |
| 自動指標付け出力 | Packet単体をPacket配列へ集約するため |

この説明を書いた後に、00Aのルールに従って配置関数、端子名、配線順を書く。

## 12. 既存資料への適用方針

本ルール制定以前の資料を一括して書き換える必要はない。次の順で段階的に適用する。

1. 新しく作成するVI。
2. 現在実装中のVI。
3. 不具合修正または仕様変更で触るVI。
4. 複雑で質問が多い既存VI。
5. 単純な既存VI。

既存本文を維持する必要がある場合は、設計意図節をVI手順の直前または章末へ追記し、既存手順と競合する場合の優先関係を明記する。

RAMScopeでは、まず次を優先する。

```text
Parse_SYSINFO_Array.vi
RAMScope_Parse_Buffer.vi
Build_CHINFO_170_Raw.vi
Build_LOGINFO_Raw.vi
RAMScope_File_Log_*.vi
```

その後、一般機器VI、CAN、負荷電流VI、並列処理およびTestStand連携へ横展開する。

- [ ] LabVIEW関数名を使わない擬似コードを書いた
- [ ] 計算式がデータ構造から導かれる理由を書いた
- [ ] Case Structureが必要な条件分岐を説明した
- [ ] Forループの1反復の処理単位を説明した
- [ ] Whileループの停止条件とTimeoutを説明した
- [ ] Shift Registerで保持する状態と理由を説明した

この確認表を満たさない資料は、VIを再現できても設計を学べないため、学習型実装資料として未完成と判断する。

## トップVIの出力ソースを説明する

トップVIでは、出力一覧だけでなく次を示す。

```text
出力名
  → 元となるSubVI
  → 元端子
  → 分岐位置
  → Caseを通る場合のTrue側接続
  → Caseを通る場合のFalse側接続
  → 最終表示器またはコネクタペーン
```

状態管理では、Boolean名だけでなく更新式を擬似コードで示す。Cleanupでは、通常処理の最初のエラーを保持しながらStop、Release、Closeを試す理由を説明する。
