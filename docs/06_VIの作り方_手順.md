# 06. VI の作り方（具体的手順）

ここでは「1イベント1VI」を新規作成する具体的ステップを示す。
例として **`RZX_Voltage_Set.vi`（高圧電源の電圧設定）** を作る流れで説明する。
他の VI も同じ手順で量産できる。

## 6.1 共通の型定義を先に作る（最初に1回）

> **用語の注意（取り違え注意）**：ここで作るのは **「制御器（Control／`.ctl` ファイル）」** であって、
> **「コントローラ（Controller）」ではない**。
> - 制御器 / コントロール（Control）= `.ctl` ファイル ← **これが目的**
> - コントローラ（Controller）= VI のデザインパターン（生産者/消費者ループの雛形）← 無関係
>
> 「新規」ダイアログのデザインパターンにある「コントローラ/ワーカのデザインパターン」を
> 選ばないこと。日本語 LabVIEW では **「制御器」または「タイプ定義」** がこれにあたる。

### 手順（推奨：タイプ定義を直接作る近道）

1. プロジェクトで右クリック → `新規（New）`。
   → 出てくる「新規」ダイアログで **「他のファイル」を展開 → `タイプ定義（Type Definition）`** を選んで OK。
2. 開いた**カスタム制御器エディタ**（`.ctl` 専用ウィンドウ）に Enum（列挙体）を配置
   → 右クリック → `項目を編集（Edit Items）`で `OK / Warning / Error / Timeout` を入力。
3. 「タイプ定義」を選んで開いた場合、**ツールバー左上のドロップダウンはすでに `タイプ定義` になっている**
   （ドロップダウンを変更する手順は不要）。
4. `Status.ctl` として `00_Common`（実フォルダ）に保存。保存先・フォルダの考え方は
   [03_LabVIEW環境構築.md](./03_LabVIEW環境構築.md) 3.5.1 を参照。
5. 同様に `TestError.ctl`（クラスタ：機器名・コード・メッセージ・時刻・致命度）を作成
   （Enum の代わりに Cluster を配置し、その中に各要素を入れる）。

> **別法（「制御器」やブランクVIから作る場合）**：
> - **「他のファイル → 制御器（カスタム制御器）」から作った場合**は、エディタが「制御器」モードで開く。
>   ツールバー左上のドロップダウンを `制御器（Control）` → **`タイプ定義（Type Def.）`** に変更してから保存する。
> - **普通のフロントパネルに Enum を置いて作る場合**は、その Enum を右クリック →
>   **「タイプ定義に指定」** を選ぶと型定義化できる（→ その後 `Status.ctl` として保存）。
> いずれの方法でも最終的に「型定義された `.ctl`」ができれば同じ。上記 1〜3 の
> 「タイプ定義を直接選ぶ」方法が最も手数が少ない。

### 6.1.1 2 つの型定義の中身（作り分け）

| 型定義 | 中身 | 理由 |
|--------|------|------|
| `Status.ctl` | **Enum（列挙帯）** | 実行結果は `OK / Warning / Error / Timeout` の**1つの選択肢**だから |
| `TestError.ctl` | **Cluster（クラスタ）** | 複数の異なる型を1つにまとめるから（下表）|

**`TestError.ctl`（クラスタ）の要素と型：**

| 要素（ラベル）| 制御器の型 | 備考 |
|--------------|-----------|------|
| `機器名` | 文字列（String）| どの機器のエラーか（`RZX` / `PPX` / `DLM5058` 等）|
| `コード` | **数値（I32 または U32）** | エラーコード（下記の型の選び方を参照）|
| `メッセージ` | 文字列（String）| エラー内容の説明 |
| `時刻` | タイムスタンプ（Timestamp）| 発生時刻 |
| `致命的` | ブール（Boolean）| `True`＝致命的（Cleanup で即シャットダウン）。TestStand の中断判定に使う。段階が必要なら Enum `{警告/エラー/致命的}` でも可 |

> **`コード` の型（I32 / U32）の選び方**：
> - **SCPI 機器（RZ-X2 / PPX）のコードのみ**を格納 → **I32**（`-100`〜`-906` の負数コードをそのまま扱える）。
> - **RAMScope の 16 進コード**（`0xE0000004` 等、[10](./10_RAMScope実装方針.md) 参照）**も同じクラスタに格納する** →
>   I32 では範囲を超えて負数に化けるため **U32** にする。
> - 迷う場合は **U32** が無難（RAMScope コードまで正しく表示可能。SCPI の負数コードは
>   機器側で符号を調整するか別途扱う前提）。本システムで RAMScope を含める場合は U32 を推奨。

**作成手順（クラスタ）**：グレーのクラスタ枠の**内側**に上記5要素をドロップ →
各ラベルを設定 → `TestError.ctl` として `00_Common` に保存。
（要素は必ず枠の内側に置く。外に置くと別々の制御器になる。狭ければ枠の角をドラッグして拡大）

> 以降、全 VI でこの型定義を「ステータス出力」「エラー情報出力」に使う。

### 6.1.2 共通サブVI `Error_To_TestStatus.vi`（生エラー→型定義への変換を1箇所にまとめる）

ドライバ VI（計装ドライバ／SCPI VI いずれも）が返す `error out` は**標準の error cluster**
（`status`/`code`/`source`）であり、これを毎回 `Status.ctl`／`TestError.ctl` に変換するロジックを
VI ごとに書くと重複・ブレの元になる。**`00_Common` に共通サブVIとして 1 つ作り、
以降の全 VI（機器を問わず）から呼び出す**。

**なぜこの設計にするのか（作りながら疑問になりやすい点）：**

- **Q. なぜ入力に `機器名` が要るのか？　`error out` にはつながらないのに？**
  → その通りで、`機器名` は標準の `error out` には**つながらない**。行き先は
  **このサブVIの内部で新しく組み立てる `TestError.ctl` の中の `機器名` 要素**（後述の内部ロジックで
  Bundle する）。このサブVIは FG420 専用ではなく **RZX／PPX／RAMScope 等すべての機器で使い回す
  汎用部品**として設計しているため、サブVI自身は「今どの機器のために呼ばれているか」を知らない。
  だから呼び出し側が `"FG420"` のような文字列で**教えてやる**必要がある。

- **Q. なぜ「標準エラークラスタ（`error out`）」と「`TestError.ctl`」を両方出すのか？**
  → **読む相手が違う**ため。

  | 出力 | 読む相手 | 理由 |
  |------|---------|------|
  | `error out`（標準 error cluster）| ①次のドライバ VI の `error in`（doc05 5.5 のエラースキップ判定は**標準の型**でないと配線できない）／②TestStand 自身（標準クラスタなら TestStand が自動でステップ失敗を検知できる）| **LabVIEW/TestStand の組み込み機能とつながるための共通言語** |
  | `TestError.ctl` + `Status.ctl` | この試験システム独自のログ・レポート・Cleanup判定ロジック | 標準クラスタには無い「どの機器か（機器名）」「致命的か」「発生時刻」を持つ**この案件専用の拡張フォーマット** |

  つまり `error out` は「LabVIEW/TestStand への標準の申告」、`TestError.ctl` は
  「この試験システム独自の詳細レポート」という役割分担。

**入出力：**

| 端子 | 型 | 説明 |
|------|----|------|
| `error in` | error cluster（標準）| ドライバ VI の生エラー出力をそのまま受ける |
| `機器名` | String | 呼び出し側が `"FG420"` 等を渡す（**注意**：`TestError.ctl` クラスタ内部にも同名の要素 `機器名` があるが、これは**別物**。クラスタ内部の要素は外部の入力端子として直接使えないため、独立した文字列制御器を新設する）|
| `実行結果ステータス` | `Status.ctl`（出力）| `error in.status = False` → `OK` ／ `True` → `Error` |
| `エラー情報` | `TestError.ctl`（出力）| `機器名`＝入力の値／`コード`＝`error in.code`／`メッセージ`＝`error in.source`／`時刻`＝現在時刻／`致命的`＝`error in.status` |
| `error out` | error cluster（標準）| `error in` をそのまま後段へ通す |

**フロントパネルへの配置手順（ハマりやすい点）：**

1. `error in`／`error out`：`関数パレット`から探すより、**呼び出し元VI（例：`FG420_Init.vi`）の
   ドライバ VI の `Error Out` 端子を右クリック→「制御器を作成」**すると正しい型の error cluster が
   自動生成される。それをコピーしてこのサブVIの `error in`／`error out` として使う。
2. `実行結果ステータス`（`Status.ctl`）・`エラー情報`（`TestError.ctl`）：プロジェクトツリーの
   `00_Common` から `.ctl` をフロントパネルへドラッグ&ドロップする。
   > 🔴 **重要な注意**：ドラッグ&ドロップすると**デフォルトでは「制御器（入力）」として配置される**。
   > このサブVIでは**出力として使いたい**ため、配置後に**右クリック→「制御器を表示器に変更」**
   > を選ぶ必要がある。変更し忘れると、後でこの端子に配線しようとしても
   > 「出力として配線できない」状態になり、原因が分かりにくい（本プロジェクトで実際にハマった点）。
3. `機器名`：クラスタの外に**新規の文字列制御器**を1つ配置する（6.1.1 のクラスタ内`機器名`とは別）。

**内部ロジックの組み方（ブロックダイアグラム）：**

> 上記までは「入出力の器（フロントパネル）」を作った段階。ここからが実際に
> `error in` を判定して `Status.ctl`／`TestError.ctl` を組み立てる**中身の処理**。
> 器と中身を分けて段階的に作るのは、コネクタペイン（呼び出し方）を先に固定してしまえば、
> 中身を後から直しても呼び出し側の配線に影響しないため（変更の影響範囲を小さくする狙い）。

```
[error in] ──▶ Unbundle By Name ──▶ status, code, source
                                        │
                      ┌─────────────────┘
                      ▼
            Case Structure（status で分岐）

 ┌─ False（エラー無し）───────────┐  ┌─ True（エラー有り）──────────────┐
 │ 実行結果ステータス = OK        │  │ 実行結果ステータス = Error        │
 │ TestError.ctl を Bundle By Name│  │ TestError.ctl を Bundle By Name  │
 │   機器名 = [機器名 入力]        │  │   機器名 = [機器名 入力]          │
 │   コード = 0                   │  │   コード = code（Unbundle した値）│
 │   メッセージ = ""               │  │   メッセージ = source（同上）     │
 │   時刻 = 現在時刻               │  │   時刻 = 現在時刻                │
 │   致命的 = False               │  │   致命的 = True                  │
 └─────────────────────────────────┘  └───────────────────────────────────┘
                      │
                      ▼
            [error out] = [error in]（Case Structure の外でそのまま素通り）
```

具体操作：

1. `error in` 端子から**関数パレット→クラスタ、クラス&バリアント→Unbundle By Name**を配線。
   ノードをクリックし `status`・`code`・`source` の3つを選ぶ。
2. **Case Structure**（関数パレット→ストラクチャ）を配置し、選択子端子に `status`（Boolean）を配線
   → 自動的に True/False の2ケースになる。
3. 各ケースの中に**Bundle By Name**（クラスタパレット）を配置。
   - `エラー情報` の出力端子で右クリック→「定数を作成」で `TestError.ctl` 型の定数を作り、
     それを Bundle By Name の左側に接続すると型が固定される。
   - ノードをクリックして埋めたい項目（機器名・コード・メッセージ・時刻・致命的）を選び、それぞれ配線。
4. `実行結果ステータス` も同様に、各ケースで `Status.ctl` 型の定数（`OK`／`Error`）を作って配線。
5. `時刻` には**「現在の日付/時刻を取得」**（関数パレット→時間、ダイアログ&ファイルI/O→日付/時刻）を
   そのまま配線する（タイムスタンプ型に自動変換される）。
6. `error out` は `error in` を Case Structure の**外側**でそのまま素通りさせる
   （Case の中でわざわざ複製・分岐する必要はない）。

**呼び出し側（例：`FG420_Init.vi`）での配線：**

```
YKFG400 Initialize ──▶ Error Out(生クラスタ)
                              │
                              ▼
                    Error_To_TestStatus.vi（機器名="FG420"定数を配線）
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
      実行結果ステータス   エラー情報      error out
       (Status.ctl)     (TestError.ctl)
```

> 🔴 **もう1つの注意**：サブVIの**出力端子は1つずつ個別に配線する**必要がある。
> `error out` だけ配線して `実行結果ステータス`／`エラー情報` の配線を忘れても、
> LabVIEW はエラーにしない（未配線の表示器は初期値のまま何も更新されないだけで、
> 実行不可＝壊れた配線にはならないため気づきにくい）。配線後は必ず下記の方法で検証する。

**動作検証（実機が無くても可能）：**

呼び出し元VIの `Initialize` は、実在しない VISA リソースに対して発行すると**必ずエラーを返す**。
これを「天然のエラー注入」として利用し、実機が無い段階でも配線が正しいか確認できる。

1. 実機を接続していない（または存在しない VISA リソース名の）状態で呼び出し元VIを実行。
2. `実行結果ステータス` が `OK` のままなら**配線されていない**（エラーが起きたのに `OK` はおかしい）。
   `Error` に変わっていれば正しい。
3. `エラー情報` の `機器名` が空欄のままなら未配線、`"FG420"` 等が表示されていれば正しい。

> 以降、FG420 系だけでなく、RZX／PPX／RAMScope 系のラッパ VI もすべてこの
> `Error_To_TestStatus.vi` を呼ぶだけでよい（`機器名` に渡す文字列だけ機器ごとに変える）。

## 6.2 VI の新規作成と入出力配置

1. プロジェクトで右クリック → `New` → `VI`。
2. **フロントパネル** に入力（Control）と出力（Indicator）を配置する。
   - 入力：`機器リファレンス in`（VISA リソース）、`電圧条件`（DBL）、`error in`（error cluster）
   - 出力：`機器リファレンス out`、`実行結果ステータス`（`Status.ctl`）、`エラー情報`（`TestError.ctl`）、`error out`
3. **ブロックダイアグラム** で処理を作る（後述 6.3）。

## 6.3 ブロックダイアグラムの作り込み（SCPI 機器の例）

VISA で SCPI コマンドを送る最小構成。

```
[error in]──┐
            ▼
        ┌─ Case Structure (No Error) ────────────────────┐
[Vref]─▶│  [Format Into String] "SOUR:VOLT %f"  ← 電圧条件 │
[電圧]──▶│        │                                        │
        │        ▼                                         │
        │   [VISA Write] ── [VISA Read]?(必要時 *OPC?)     │
        │        │                                         │
        │        ▼                                         │
        │   ステータス=OK / エラー時=Error をセット          │
        └──────────────────────────────────────────────────┘
            ▼
[Vref out] [Status] [TestError] [error out]
```

具体ステップ：
1. `error in` を **Case Structure** に配線し、`No Error` ケースに実処理を置く。
2. `Format Into String` で SCPI コマンド文字列を生成
   （例：`SOUR:VOLT %f` に電圧条件を埋め込む。実際のコマンドは機器マニュアル参照）。
3. **VISA Write** で機器へ送信。設定確認が必要なら `*OPC?` 等を **VISA Read** で受信。
4. 機器のエラーレジスタ（`SYST:ERR?` 等）を確認し、異常があれば
   - `実行結果ステータス` = `Error`
   - `エラー情報`（`TestError.ctl`）に機器名・コード・メッセージ・時刻を設定
5. `Error` ケース側はリファレンスをそのまま通し、ステータス=`Error` を出力。

> 計装ドライバ（Plug and Play VI）がある場合は、`VISA Write/Read` の代わりに
> ドライバ VI（例：`...Configure Voltage.vi`）を置くだけでよい。

## 6.4 コネクタペインの割り当て（TestStand から呼ぶために必須）

1. フロントパネル右上の **コネクタペイン**（端子のます目）を右クリック → `Patterns` で
   入出力数に合うパターン（例：4×2×2×4）を選ぶ。
2. 端子をクリック → 対応するフロントパネルの Control/Indicator をクリックして割り当てる。
3. **入出力の並びを全 VI で統一**する（左上＝リファレンス、左下＝error in、右上＝リファレンス out、右下＝error out など）。
   → TestStand のステップ作成・流用が定型化できる。
4. 右上のアイコンを編集し、機器が分かるアイコンにする（任意だが推奨）。

## 6.5 単体テスト（VI 単体動作確認）

1. フロントパネルに値を入れ、実行（▶）。機器が期待どおり動くか確認。
2. 異常系（error in にエラーを入れる、機器を切断する）でも
   ステータス／エラー情報が正しく出るか確認。
3. 問題なければ保存し、TestStand から呼べる状態にする。

## 6.6 VI 量産のコツ（テンプレート化）

1. 上記で作った VI を **「ひな形 VI（テンプレート）」** として保存
   （例：`_Template_Instrument.vi`）。
2. 新しいイベント VI を作るときはテンプレートを複製し、
   - 入力の試験条件
   - 送る SCPI コマンド / ドライバ VI
   - 機器名（エラー情報用）
   だけを差し替える。
3. これにより、入出力仕様・エラー処理が全 VI で統一され、保守性が上がる。
