# 06. VI の作り方（共通手順）

> **本章の役割**：機器を問わず使用する型定義、共通エラー変換、VI雛形の作り方を説明する。
>
> 本章の手順は[00A](./00A_LabVIEW実装資料の記述ルール.md)に従う。RAMScope固有のCLFN、typedef、数値変換、Builder、Parserは[10](./10_RAMScope実装方針.md)を正とする。
>
> **2026-07-26更新**：各VIの作成前に[00C](./00C_一次資料とバージョン基準.md)の証跡欄を埋める。NI関数はNI公式Help、機器ドライバVIは配布元マニュアルと実コネクタペイン、DLLは同梱ヘッダを優先する。

## 6.1 最初に作る共通部品

### なぜ先に作るのか

各機器VIを先に作ると、Status、エラー情報、コネクタペインがVIごとに異なる。共通型と変換VIを先に作り、以降の公開APIを同じ端子構成へそろえる。

```text
00_Common\
├─ Status.ctl
├─ TestError.ctl
└─ Error_To_TestStatus.vi
```

RAMScope固有の共通部品は`30_RAMScope\00_Common`へ作成する。

```text
30_RAMScope\00_Common\
├─ RAMScope_Code_To_Error.vi
├─ RAMScope_Channel.ctl
├─ RAMScope_Meas_Config.ctl
├─ RAMScope_Module_Log_Config.ctl
├─ RAMScope_Module_Info.ctl
├─ RAMScope_Channel_Value.ctl
├─ RAMScope_Packet.ctl
├─ RAMScope_Byte_Order.ctl
└─ 数値⇔U8変換VI
```

## 6.2 `Status.ctl`

### 0. 目的

公開APIの結果を、TestStandが共通の値で判定できるようにする。

### 1. 入出力

`Status.ctl`は列挙体のtypedefであり、VIではないため入出力端子は持たない。

### 2. 配置する制御器

| 数 | 日本語名 | 英語名 | 配置場所 |
|---:|---|---|---|
| 1 | 列挙体 | Enum | 制御器パレット → リング&列挙体 |

### 3. 作成手順

1. プロジェクトエクスプローラの`00_Common`を右クリックする。
2. `新規 → タイプ定義`を選ぶ。
3. 制御器エディタが開いたことを確認する。
4. 初期配置された不要な制御器がある場合は削除する。
5. 列挙体（Enum）を配置する。
6. 列挙体を右クリックし、項目を編集する。
7. 次を上から順に登録する。

```text
OK
Warning
Error
Timeout
```

8. ラベルを`Status`へ変更する。
9. `Status.ctl`として`00_Common`へ保存する。
10. 制御器エディタ上部の種類が`タイプ定義（Type Def.）`であることを確認する。

> `新規 → タイプ定義`から作成した場合、後からカスタム制御器を`Type Def.`へ変更する操作は不要である。

### 4. 単体確認

1. 新規VIへ`Status.ctl`を配置する。
2. 列挙値として`OK / Warning / Error / Timeout`を選択できることを確認する。
3. `Status.ctl`へ項目を追加した場合、配置済み端子へ変更が反映されることを確認する。

## 6.3 `TestError.ctl`

### 0. 目的

標準error clusterだけでは不足する機器名、時刻、致命度を共通形式で保持する。

### 1. フィールド

| 要素 | 型 | 用途 |
|---|---|---|
| `機器名` | String | `RAMScope`、`DLM5058`等 |
| `コード` | U32 | 機器固有32bitコードをビット列どおり保持 |
| `メッセージ` | String | 人が読める説明 |
| `時刻` | Timestamp | エラー発生時刻 |
| `致命的` | BooleanまたはEnum | Cleanup・中断判定 |

### 2. 配置する制御器

| 数 | 日本語名 | 英語名 | 配置場所 |
|---:|---|---|---|
| 1 | クラスタ | Cluster | 制御器パレット → 配列、行列&クラスタ |
| 2 | 文字列制御器 | String Control | 制御器パレット → 文字列&パス |
| 1 | 数値制御器 | Numeric Control | 制御器パレット → 数値 |
| 1 | タイムスタンプ | Time Stamp | 制御器パレット → 数値 |
| 1 | ブール制御器 | Boolean Control | 制御器パレット → ブール |

### 3. 作成手順

1. `00_Common`を右クリックし、`新規 → タイプ定義`を選ぶ。
2. クラスタ（Cluster）を配置する。
3. 文字列制御器を2個クラスタ内へ置き、`機器名`と`メッセージ`へ変更する。
4. 数値制御器をクラスタ内へ置き、ラベルを`コード`へ変更する。
5. `コード`を右クリックし、`表現形式 → 符号なし32ビット整数（U32）`へ変更する。
6. タイムスタンプ制御器を置き、ラベルを`時刻`へ変更する。
7. ブール制御器を置き、ラベルを`致命的`へ変更する。
8. タブ順またはクラスタ順序を、表の上から順になるように確認する。
9. `TestError.ctl`として保存する。

標準error clusterの`code`はI32である。U32へ渡す場合は型変換（Type Cast）でビット列を保持する。

### 4. 単体確認

- `コード`のワイヤがU32の青色である。
- クラスタを名前でバンドル（Bundle By Name）へ接続したとき、5フィールドを名前で選択できる。

## 6.4 `Error_To_TestStatus.vi`

<!-- generated-vi-diagram -->
![ErrorToTestStatus.vi 入出力イメージ](./assets/vi-diagrams/errortoteststatus.svg)

### 0. 目的と処理概要

標準error clusterを、TestStand用の`Status.ctl`と`TestError.ctl`へ変換する。元のerror clusterは変更せず、そのまま`error out`へ渡す。

### 1. 入出力

| 端子 | 方向 | 型 | 用途 |
|---|---|---|---|
| `error in` | 入力 | error cluster | 前段エラー |
| `機器名` | 入力 | String | TestErrorへ記録する機器名 |
| `実行結果ステータス` | 出力 | `Status.ctl` | OKまたはError |
| `エラー情報` | 出力 | `TestError.ctl` | 詳細エラー情報 |
| `error out` | 出力 | error cluster | 元のerror cluster |

### 2. 配置する関数およびSubVI等

| 数 | 日本語名 | 英語名 | 配置場所 |
|---:|---|---|---|
| 1 | 名前でバンドル解除 | Unbundle By Name | プログラミング → クラスタ、クラス、バリアント |
| 1 | ケースストラクチャ | Case Structure | プログラミング → ストラクチャ |
| 1 | 型変換 | Type Cast | プログラミング → 数値 → データ操作 |
| 2 | 名前でバンドル | Bundle By Name | プログラミング → クラスタ、クラス、バリアント |
| 1 | 日付/時間を秒で取得 | Get Date/Time In Seconds | プログラミング → タイミング |
| 1 | `Status.ctl`定数 | typedef constant | `00_Common` |
| 1 | `TestError.ctl`定数 | typedef constant | `00_Common` |

### 3. 配線順

1. `error in`を名前でバンドル解除（Unbundle By Name）へ接続する。
2. 要素を広げ、`status`、`code`、`source`を表示する。
3. `status`のBoolean出力をケースストラクチャ（Case Structure）のセレクタへ接続する。
4. `error in`のワイヤを分岐し、ケースストラクチャを通さず`error out`へ直接接続する。

#### Falseケース：エラーなし

5. `Status.ctl`定数を配置し、値を`OK`へ設定する。
6. `Status.ctl`定数を`実行結果ステータス`出力トンネルへ接続する。
7. `TestError.ctl`定数を名前でバンドル（Bundle By Name）の基準クラスタへ接続する。
8. `機器名`入力を`機器名`フィールドへ接続する。
9. U32定数`0`を`コード`へ接続する。
10. 空文字列定数を`メッセージ`へ接続する。
11. 日付/時間を秒で取得（Get Date/Time In Seconds）の出力を`時刻`へ接続する。
12. Boolean定数Falseを`致命的`へ接続する。
13. 名前でバンドル出力を`エラー情報`出力トンネルへ接続する。

#### Trueケース：エラーあり

14. `Status.ctl`定数を配置し、値を`Error`へ設定する。
15. `Status.ctl`定数を`実行結果ステータス`出力トンネルへ接続する。
16. 型変換（Type Cast）を配置する。
17. `code` I32を型変換の`x`入力へ接続する。
18. U32定数`0`を型変換の`type`入力へ接続する。
19. 型変換のU32出力を、2個目の名前でバンドルの`コード`へ接続する。
20. `機器名`入力を`機器名`へ接続する。
21. `source`文字列を`メッセージ`へ接続する。
22. 日付/時間を秒で取得の出力を`時刻`へ接続する。
23. Boolean定数Trueを`致命的`へ接続する。
24. 名前でバンドル出力を`エラー情報`出力トンネルへ接続する。
25. False/True両ケースで`実行結果ステータス`と`エラー情報`の出力トンネルが配線済みであることを確認する。

### 4. 単体テスト

| error in | 機器名 | 期待Status | 期待TestError |
|---|---|---|---|
| 正常 | `RAMScope` | OK | code=0、致命的=False |
| status=True、code=-1234、source=`Existing error` | `RAMScope` | Error | U32ビット列、メッセージ=`Existing error`、致命的=True |

確認項目：

- `error out`が`error in`と一致する。
- エラー時のU32コードがI32のビット列を保持する。

## 6.6 一般的な公開API VIの雛形

### 0. 目的

機器固有の下位処理をTestStandから呼びやすい1イベントへまとめる。

### 1. 共通端子

| 方向 | 端子 |
|---|---|
| 入力 | 試験条件、`error in`、必要な場合だけ機器リファレンスin |
| 出力 | 計測値、Status、TestError、`error out`、必要な場合だけリファレンスout |

### 2. 配置する関数・SubVI

公開APIごとに、次を一覧化する。

- 下位ドライバVIまたはDLLラッパ
- Builder / Parser
- 名前でバンドル解除（Unbundle By Name）
- ケースストラクチャ（Case Structure）
- `Error_To_TestStatus.vi`

### 3. 共通配線順

1. `error in`を名前でバンドル解除し、`status`を外側ケースストラクチャへ接続する。
2. Trueケースでは主要出力へ安全な初期値を接続し、元の`error in`を後段へ渡す。
3. Falseケースで機器操作または下位SubVIを呼ぶ。
4. 複数SubVIのerror clusterを左から右へ直列接続する。
5. 最後のerror clusterを`Error_To_TestStatus.vi`の`error in`へ接続する。
6. 機器名文字列定数を`Error_To_TestStatus.vi`の`機器名`へ接続する。
7. Status、TestError、error outを本VIの出力へ接続する。

### SCPI / 計装ドライバVI

- VISA Write / VISA Readまたはメーカー提供VIを配置する。
- 設定値は入力端子から受け取る。
- 固定仕様だけを定数にする。
- VISAリファレンスin/outを直列で渡す。
- Set処理は可能な場合にQueryで読み返し、Verifyする。

### RAMScope公開API

- `RS_DLL_*`またはData Conversion VIを呼ぶ。
- DLLラッパ内でReturnCodeは`RAMScope_Code_To_Error.vi`へ接続済みとする。
- RAMScopeにはVISAリファレンス端子を追加しない。

## 6.7 RAMScope DLLラッパの雛形

### 0. 目的

1個のC関数呼び出しだけを隔離し、CLFN設定と上位ロジックを分離する。

### 1. 共通入出力

```text
入力 : API引数、error in
出力 : API固有出力、API ReturnCode、error out
```

### 2. 配置する関数・SubVI

- ライブラリ関数呼び出しノード（Call Library Function Node）1個
- `RAMScope_Code_To_Error.vi`1個
- 通常ラッパではCase Structure 1個

### 3. 共通配線順

1. `error in.status`でCLFN実行をガードする。
2. FalseケースでCLFNへすべてのAPI引数を接続する。
3. CLFN ReturnCodeを`RAMScope_Code_To_Error.vi`の`API ReturnCode`へ接続する。
4. CLFN error outを同SubVIの`error in`へ接続する。
5. 関数名文字列を`Function Name`へ接続する。
6. SubVIの`error out`を本ラッパの`error out`へ接続する。
7. `Status.ctl`と`TestError.ctl`は生成しない。
8. Builder、Parser、複数関数の順序制御を入れない。

`DeviceExit`等のCleanup用ラッパは、前段エラーがあってもCLFNを呼ぶ例外設計とする。

## 6.8 フロントパネルとコネクタペイン

### 公開する端子

- TestStandから変更する条件
- 後段へ渡す値
- `error in / error out`
- Status
- TestError
- 必要な機器リファレンス

### 公開しないもの

- 固定する単位、モード、内部用定数
- デバッグ専用値
- 使用しないドライバ出力

### 推奨配置

```text
左上 : 主要入力
左下 : error in
右上 : 主要出力
右下 : error out
```

コネクタペインへ割り当てた後、Context Helpで端子名と必須・推奨・任意の状態を確認する。

## 6.9 Cleanup VIの例外

通常VIは前段エラーで実処理をスキップする。Cleanup VIは前段エラーがあっても終了処理を試みる。

```text
元のerror in ─────────────────────────────┐
                                           ├→ エラーをマージ（Merge Errors）
エラーなしクラスタ → Close処理 → Close error ┘
```

手順には、Close処理へ正常クラスタを渡す方法と、元エラーをどの入力へ接続するかを明記する。RAMScopeでは`RAMScope_Close.vi`が該当する。

## 6.10 単体テスト

### 正常系

- 実機またはダミーデータが期待どおり動作する。
- Statusが`OK`。
- error outが正常。
- 設定値、取得値、戻り値が仕様どおり。
- 配列サイズとフィールド位置が期待どおり。

### 異常系

- error inへ意図的にエラーを入れ、通常VIが処理をスキップする。
- 入力配列を不足サイズへ変更する。
- 範囲外・重複入力を与える。
- 機器切断でErrorとTestErrorを出力する。
- Cleanup VIが前段エラーに関係なく終了処理を試みる。

### ダミーデータ

構造体や生バイト列を試験する場合は、次を手順へ書く。

```text
配列初期化（Initialize Array）の要素型と要素数
部分配列置換（Replace Array Subset）のindex
new element/subarrayへ入れる配列値
期待する出力位置
```

## 6.13 全VI共通の作成前・作成後記録

### 0. 目的

同じVI名でもドライバVersionによって端子や既定値が異なる可能性があるため、配置前に根拠を固定し、完成後に実配線と資料を照合できるようにする。

### 1. 作成前記録

```text
Source:
Version:
Symbol:
Signature:
Verified by:
State:
```

- NI標準関数はContext Help（Ctrl+H）とNI公式Helpで確認する。
- 計装ドライバVIはVI Tree、Context Help、フロントパネル、コネクタペインを確認する。
- DLL Wrapperはヘッダ宣言とCLFN Parametersを引数順に並べて照合する。
- ActiveXは対象PCのType LibraryからProperty／Methodを選択し、文字入力でメンバ名を作らない。

### 2. 作成順

1. 新規VIを決められたレイヤフォルダへ保存する。
2. フロントパネルへ入力制御器、出力表示器、`error in`、`error out`を配置する。
3. 各端子のRepresentation、配列次元、typedef状態、既定値を決める。
4. コネクタペインへ必須端子を割り当てる。
5. 必要なCase Structure／Loopを先に配置し、selector、N端子、停止条件を接続する。
6. 各構造の内側へ関数とSubVIを配置する。
7. 全Caseの全出力トンネルを接続する。
8. error wire、参照wire、状態wire、データwireの順で接続を追跡する。
9. VI Descriptionと各端子Descriptionへ単位、範囲、所有権を記載する。
10. 正常、境界、異常、既存エラー入力を試験する。

### 3. 完成後レビュー表

| 確認 | 合格条件 |
|---|---|
| VI構成 | 既決VIを改名、統合、分割していない |
| 端子 | 資料の型、方向、次元、既定値と一致 |
| 構造 | Case／Loopの必要性がアルゴリズムから説明されている |
| Case | selector式とTrue／Falseの意味が明記され、全出力が配線済み |
| error | 既存errorを上書きせず、Cleanupの例外だけを明示 |
| Source | 公式Helpまたはベンダー資料まで追跡できる |
| Test | 入力方法、期待値、観測場所が記載されている |

| 機器 | VI |
|---|---|
| DLM5058 | Init / Config / Acquire_Start / Acquire_Stop / Save_Waveform / Close |
| MX100 | Init / Log_Start / Read / Log_Stop / Save / Close |
| RAMScope | Connect / Init / Set_Cond / Log_Start / Read / Release / Log_Stop / Close |
| RZ-X | Init / Voltage_Set / Current_Limit_Set / Output_On / Output_Off / Read / Close |
| PPX | Init / Voltage_Set / Output_On / Output_Off / Read / Close |
| CAN | Open / Send / Read / Close（採用方式に応じる） |
