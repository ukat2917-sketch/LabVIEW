## 2. 情報の優先順位

矛盾がある場合は次の順で判断する。

1. メーカー提供ヘッダ、プログラミングマニュアル、サンプル
2. 実機で再現できた検証結果
3. 本リポジトリの「正本」と指定された章
4. 検討案、参考例、過去のメモ

## 3. 状態ラベル

| 表記 | 意味 |
|------|------|
| **確定** | 一次情報または実機結果で確認済み |
| **PoC済み** | 最小構成で動作確認済み。全機能・長時間試験は未実施 |
| **実機確認待ち** | 設計・型は整理済みだが、対象機器を接続した検証が未完了 |
| **未決定** | 候補比較中。実装ルートとして固定しない |
| **参考** | 採用しない案、過去情報、代替手段 |

未確認の内容を「必須」「正常」「原因確定」と断定しない。

## 5. RAMScopeの現在の確定事項

- LabVIEW 64bitを使用する。
- RAMScopeVP API 64bit版をCLFNから直接呼ぶ。
- API DLLは`RAMScopeVP_API_x64.dll`。
- GT170はUSB3.0で接続する。
- Visual C++ 2013 Redistributable x64を利用可能にする。
- 64bit APIフォルダへx86版`mfc120*` / `msvc*120`を混在させない。
- `RAMScopeGT150DeviceInit`をGT170の接続処理にも使用する。
- 最初に作成したDeviceInit VIは`RAMScope_Connect.vi`とする。
- `RAMScope_Init.vi`は`AllInit + GetSysInfo`を担当する。
- API ReturnCodeとCLFNの`error out`を別々に評価する。
- `RAMScope_Close.vi`はCleanupで必ず実行する。

## 6. RAMScopeの未確定事項

- GT170実機接続時のDeviceInit正常値
- `0x30100001`の正式定義
- AllInit以降の通し動作
- 実データのEndianとTimestamp
- `ReleaseBufferData`の必須性
- APIのスレッドセーフ性
- RAMScope CAN機能を本番CAN方式として採用するか

## 7. 更新時のルール

1. 新しい事実を得たら、最初に正本を更新する。
2. READMEと13章の現在地を更新する。
3. 同じ説明を複数章へ詳細に複製しない。詳細は正本へリンクする。
4. 過去案を残す場合は「参考」「不採用」「旧情報」と明記する。
5. 関数名、VI名、ファイル名は大文字小文字を含めて統一する。
6. 実機未確認の値には、確認日、環境、観測条件を付ける。
7. Cleanupと安全要件の変更は、11章と12章の両方へ反映する。
