# 02. 役割分担とアーキテクチャ

> **本章の役割**：LabVIEWとTestStandの責務境界を定義する。
>
> 本章は設計方針の正本であり、VIの画面操作や端子単位の配線は[06](./06_VIの作り方_手順.md)、RAMScope詳細は[10](./10_RAMScope実装方針.md)を参照する。手順の記述方法は[00A](./00A_LabVIEW実装資料の記述ルール.md)に従う。

## 2.1 LabVIEWとTestStandの役割

| 項目 | LabVIEW | TestStand |
|---|---|---|
| 担当 | 1つの機器に対する最小操作 | 試験全体の順序・条件・時間・結果管理 |
| 粒度 | 1イベント1VI | VI呼び出しを組み合わせたシーケンス |
| 条件 | 入力として受け取る | FileGlobals / Parameters / Property Loaderで管理 |
| 待ち | 原則入れない | Waitステップで管理 |
| 分岐・繰り返し | 機器処理に必要な最小範囲 | 試験条件に応じて管理 |
| エラー | 標準error clusterと機器固有コードを出力 | 中断、継続、Cleanup、レポートを判断 |
| Cleanup | 個別の停止・終了VIを提供 | 安全順序で必ず実行 |

### 基本原則

- **何をするか**はLabVIEW VIへ実装する。
- **いつ、どの順番で、何回、どの条件で行うか**はTestStandへ実装する。
- VIは呼ばれた処理を完了して返す。
- 試験都合の待ち時間やシナリオ分岐をVI内部へ埋め込まない。

## 2.2 RAMScopeの公開API粒度

| 公開API | TestStandから見たイベント | 内部で呼ぶ主な処理 |
|---|---|---|
| `RAMScope_Connect.vi` | 接続 | DeviceInit |
| `RAMScope_Init.vi` | 初期化 | AllInit、GetSysInfo、SYSINFO解析、PGT設定 |
| `RAMScope_Set_Cond.vi` | 条件設定 | MEASINFO、CHINFO、LOGINFO生成と設定 |
| `RAMScope_Log_Start.vi` | 計測開始 | MeasStart |
| `RAMScope_Read.vi` | データ取得・解析 | GetBufferData、Buffer Parser |
| `RAMScope_Log_Stop.vi` | 計測停止 | MeasStop |
| `RAMScope_Release.vi` | バッファ解放候補 | ReleaseBufferData |
| `RAMScope_Close.vi` | 終了 | DeviceExit |

次は公開APIとして作成しない。

- `RAMScope_Config.vi`：PGT設定は`RAMScope_Init.vi`へ統合する。
- 公開用`RAMScope_Parse_Buffer.vi`：Parserは`20_Data_Conversion`の内部VIとし、`RAMScope_Read.vi`から呼ぶ。

## 2.3 RAMScopeの下位レイヤ

```text
30_Public / RAMScope_* 公開API
  → 00_Common / 20_Data_Conversion
      → 10_DLL_Wrapper / RS_DLL_*
          → ライブラリ関数呼び出しノード（Call Library Function Node）
              → RAMScopeVP_API_x64.dll
```

| レイヤ | 必要な理由 | 責務 |
|---|---|---|
| DLL Wrapper | CLFN設定ミスとデータ変換ミスを分けて切り分ける | DLL関数を1個だけ呼ぶ |
| Common / Data Conversion | C構造体とLabVIEW型の差を吸収する | 数値変換、Builder、Parser |
| Public API | TestStandへDLL関数名を露出させない | 下位VIを試験イベントへまとめる |
| PoC | TestStand設定とLabVIEW実装の問題を分ける | 公開APIをLabVIEW単体で順に確認する |

- DLLラッパは`Status.ctl`と`TestError.ctl`を生成しない。
- 公開APIの末尾で`Error_To_TestStatus.vi`を1回呼ぶ。

## 2.4 同期・非同期

| 種類 | 例 | 実装 |
|---|---|---|
| 同期 | 電源ON → DUT起動 → RAMScope設定 → 計測開始 | TestStandで直列実行 |
| 非同期 | 負荷電流ランプ中にCANモード送信 | 別ThreadのSequence Call |
| ポーリング | RAMScopeの表示用バッファ読み出し | TestStandループから`RAMScope_Read.vi`を反復呼び出し |

RAMScopeVP APIのスレッドセーフ性は未確認のため、同一デバイスへのDLL呼び出しを複数スレッドから同時実行しない。

## 2.5 接続状態の持ち方

### VISA機器

```text
Setup  : VISA Open
Main   : リファレンスを各操作VIへ渡す
Cleanup: VISA Close
```

### RAMScope

RAMScopeVP APIはセッションハンドルを返さず、DLL内部のグローバル状態で接続を管理する。

```text
Setup
  RAMScope_Connect.vi
  RAMScope_Init.vi
  RAMScope_Set_Cond.vi

Main
  RAMScope_Log_Start.vi
  RAMScope_Read.vi
  RAMScope_Log_Stop.vi
  RAMScope_Release.vi（要否検証中）

Cleanup
  RAMScope_Close.vi
```

RAMScope VIにはVISAリファレンス端子を追加しない。必要に応じて次を個別に渡す。

- `UnitNo`
- `MdlNo_RAM`
- `MdlNo_CAN`
- `Endian_RAM`
- `Channel List`
- 標準error cluster

`RAMScope_Context.ctl`はPoC完了まで作成しない。

## 2.6 エラー経路

| 経路 | 発生する代表例 |
|---|---|
| CLFN `error out` | DLL未検出、関数未検出、引数設定、配列ポインタ設定 |
| API ReturnCode | デバイス状態、パラメータ、接続、測定状態に関するAPI結果 |

```text
DLLラッパ内
  API ReturnCode + CLFN error out
    → RAMScope_Code_To_Error.vi
    → 標準error cluster

公開API末尾
  標準error cluster
    → Error_To_TestStatus.vi
    → Status.ctl / TestError.ctl / error out
```

## 2.7 全体アーキテクチャ

```text
┌──────────────────────── TestStand ────────────────────────┐
│ Setup   : 接続・初期化・設定                              │
│ Main    : 試験イベント、待ち、分岐、ループ、並列処理       │
│ Cleanup : 高圧停止、データ退避、DUT停止、機器終了          │
│ Variables: 条件、機器状態、取得値、ファイルパス、結果      │
└────────────────────────────┬───────────────────────────────┘
                             │ LabVIEW Adapter
┌────────────────────────────▼───────────────────────────────┐
│ LabVIEW公開API VI群                                         │
│ 1イベント1VI / 共通error in-out / Status / TestError       │
│ RAMScopeはDLL内部状態を利用し、モジュール番号等だけを渡す    │
└─────────────────────────────────────────────────────────────┘
```

## 2.8 再利用性

- 試験条件はTestStand変数として管理し、VIへハードコードしない。
- 機器固有の変換やCLFN設定はLabVIEW VIへ閉じ込める。
- 同じ機器VIを複数プロジェクトで使う場合は実体を1か所に置く。
- 未確認事項はPoC結果またはベンダー一次資料で更新する。
