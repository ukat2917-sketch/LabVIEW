# 01. システム要求とアーキテクチャ

**最終整理日:** 2026-09-03  
**State:** Design draft

---

## 1. 対象試験

本ProjectはV2L/OBC/DCDC系DUTの最大負荷試験を主対象とする。

現時点で想定する主要構成は次のとおり。

| 系統 | 機器/用途 | 現時点の情報 |
|---|---|---|
| HVDC入力 | Chroma `62180D-600D` ×2 | 最大負荷試験で2系統同時動作を想定 |
| 12V DCDC負荷 | Chroma `63206A-150-600` | 150 V / 600 A / 6 kW級 |
| V2L-2 AC負荷 | Chroma `63804` ×2 | 2系統へ各1台接続を想定 |
| OBC / V2L-1 AC系 | Chroma `61830` または `61845` | AC Source/Load系。採用型式は要確定 |
| 制御電源 | Programmable DC Source | Control / IGN / Wake等へ分岐 |
| 電力計測 | Yokogawa WT5000 | HVDC/LVDC/AC入出力電圧・電流・電力 |
| 温度 | Yokogawa SMARTDAC+ `GM10 + GX90XA` | **第一候補**。GX20はLocal displayが必要な場合のAlternative、MX100はLegacy比較対象 |
| オシロスコープ | Yokogawa `DLM5000` series | **本Projectの採用機種としてFix**。詳細型式/Option/APIは別途確定 |
| CAN | Vector CANalyzer | CAN通信・計測・必要に応じMF4記録 |
| RAM計測案A | RAMScope | 既存LabVIEW資産を流用 |
| RAM計測案B | ETAS INCA + ETK | INCA Recorderとオンライン適合を活用 |
| 統合DAQ案 | Yokogawa IS8000 | WT5000/SMARTDAC+/DLM5000/RAMScope等の統合候補 |

温度DAQは新規設備を前提とする場合、販売終了済みMX100よりSMARTDAC+系を優先する。IS8000 `/MB1`ではGM10用Modbus/TCP通信設定ファイルが提供されているため、**自動試験専用設備ではGM10を第一候補**とする。GX20は同じGX90XA module群と入手済みGX/GP/GM LabVIEW Driverを利用でき、OperatorがLocal displayを必要とする場合のAlternativeとする。詳細は[`06_温度DAQ_SMARTDAC+_GX_GM_MX100比較と仕様.md`](./06_温度DAQ_SMARTDAC+_GX_GM_MX100比較と仕様.md)を参照する。

オシロスコープについては、以降のProject設計・Adapter要求・外注仕様では**Yokogawa DLM5000シリーズを標準対象**とする。詳細型式、搭載Option、Firmware、通信Interface、公式Driver/API、IS8000との制御・記録統合可否は一次資料と実機PoCで確定する。別シリーズへの変更はProject設計変更として扱う。

別途`Xin1結線図案(1).xlsx`には、恒温槽、LLC冷却、AC/DC可変負荷、リレー制御安定化電源、パワーアナライザ、補償抵抗、CANalyzer、INCA等を含む試験環境案がある。Project実装時は最大負荷構成図とxlsxの両方を設備Inventoryへ反映し、対象設備をRun Configurationで有効/無効化できる構成を目指す。

## 2. ATSを中核にしない理由

Chroma ATSはChroma機器の自動化には利用価値があるが、今回の要求は以下を含む。

- Yokogawa、Vector、DTS INSIGHT、ETAS等を跨ぐ時系列データ管理
- CAN/RAM/電力/温度/DLM5000波形等の同一Run管理
- 同期イベントの共通化
- TestStandからの試験分岐・判定・Cleanup
- TDMS/MDF/MF4を含む統合Data Pipeline

ATSのHTML/CSV等のExportのみでは、全DAQを共通時系列として管理する中核機能には不足するため、LabVIEW + TestStandをSystem Controllerとする。

## 3. 責務分担

### 3.1 TestStand

TestStandは試験の**意図と順序**を管理する。

- Run ID生成
- 試験条件読み込み
- Setup / Main / Cleanup
- Step間依存関係
- Wait / Loop / Branch
- 合否判定
- Abort / Termination制御
- 試験結果Report
- 各Adapter公開API呼出し

TestStandからベンダーDLL、COM Ref、gRPC Client Objectを直接扱わない。

### 3.2 LabVIEW

LabVIEWは**装置とデータの実行層**を管理する。

- Device Adapter
- ベンダーDriver / VISA / COM / DLL / gRPCの隠蔽
- 非同期データ取得
- Status / Error正規化
- Run Folder / Manifest管理
- 同期Event発行
- Recorder Start/Stop Orchestration
- 必要なオンライン値のTestStand返却
- Safe State移行

### 3.3 ベンダーRecorder

高帯域・専用DAQは可能な限りベンダー側Recorderを利用する。

- SMARTDAC+ GM10/GX20: 温度等のLocal redundant recording候補
- DLM5000: 波形/Transient記録。native artifactをRunへ紐付ける
- CANalyzer: CAN記録
- INCA: ETK高速計測・MDF/MF4記録
- IS8000: Yokogawa系およびUser Library統合DAQ

LabVIEWは全量Raw Dataの唯一の通過点にはしない。

## 4. アーキテクチャ候補

### 4.1 案A: 全機器をLabVIEWへ直接統合

```text
TestStand
   ↓
LabVIEW
   ├─ Chroma Driver
   ├─ WT5000 Driver
   ├─ SMARTDAC+ GX/GM Driver
   ├─ DLM5000 Driver / VISA
   ├─ CANalyzer ActiveX
   ├─ RAMScope DLL
   └─ INCA Tool API
        ↓
      TDMS / Vendor Artifact
```

**長所**

- LabVIEW側のData Modelを統一しやすい。
- Vendor Softwareへの依存を減らせる。

**短所**

- 高速DAQをWindows/LabVIEWへ集中させる。
- ETK/CAN/RAMScope/DLM5000のRecorder機能を活かしにくい。
- Buffer/Drop/Timing責務がLabVIEWへ集中する。

### 4.2 案B: IS8000中心

```text
TestStand / LabVIEW
       ↓ gRPC
     IS8000
   ┌────┼──────────────┐
 WT5000 SMARTDAC+ GM10 DLM5000 / RAMScope(User Library)
           ↑
     Modbus/TCP / MB1
```

IS8000には次の2系統APIがある。

1. **IS8000SDK User Library**: 標準非対応測定器のDAQをIS8000へ追加する。
2. **IS8000 Control API**: 外部ApplicationからgRPCでIS8000を操作する。

SMARTDAC+ GM10はUser Libraryを新規作成するのではなく、**IS8000 `/MB1` Modbus/TCP機能を第一候補**とする。

**長所**

- Yokogawa系DAQを集約しやすい。
- GM10温度ChannelをIS8000へModbus/TCP統合できる。
- IS8000画面・Recorder・Waveform機能を利用できる。

**短所**

- CANalyzer/INCAは別系統に残る。
- GM10/GX20のModbus pollingはDL950/SL2000等の高精度同期とは別Classで評価が必要。
- DLM5000をIS8000経由でどこまで設定・波形取得・Trigger同期できるかはPoCが必要。
- RAMScope User Libraryのbit数、性能、Timestamp整合性はPoC必須。

### 4.3 推奨: Hybrid

```text
                         TestStand
                             │
                             ▼
                         LabVIEW
          ┌──────────────────┼─────────────────┐
          ▼                  ▼                 ▼
 Chroma/DLM5000 Direct   IS8000 gRPC      CANalyzer / INCA
     Adapter候補           Adapter            Adapter
                             │
                    WT5000 / SMARTDAC+ GM10 /
                    DLM5000 / optional RAMScope
                             │
                         MB1/Native

                       Run Manifest
          ┌───────────────┼───────────────┐
        TDMS      Vendor/IS8000 Artifact   CAN/INCA MF4
```

Hybridを第一候補とする理由は、各装置の専用Recorder性能を維持しながら、TestStand/LabVIEWで試験全体のStateとRun Identityを統一できるため。

温度DAQは**LabVIEW GX/GM DriverでSetup → Session Close → IS8000 MB1をRuntime ownerとしてDAQ**するOwnershipを第一候補とし、同一GM10へLabVIEWとIS8000が常時同時アクセスする構成はPoC前に標準化しない。

DLM5000については**機種をFixし、制御経路はDirect Driver/VISAとIS8000経由を比較してPoC後に1経路へFreeze**する。

## 5. 共通State Machine

各Adapterは可能な限り次の状態を持つ。

```text
Closed
  ↓ Initialize
Connected
  ↓ Configure
Configured
  ↓ Arm
Armed
  ↓ Start
Running
  ↓ Stop
Stopped
  ↓ Close
Closed
```

異常時は任意状態から`GoSafe → Stop/Close`へ遷移できること。

Recorderを持つ機器は、Device RunningとRecordingを別Stateで持ってよい。

## 6. 共通公開APIの基本形

機器ごとのnative API名が異なっても、LabVIEW Project側の公開責務は可能な範囲で揃える。

```text
Initialize / Connect
GetVersion
Configure
Arm
Start
GetStatus
ReadSelectedValues
InsertMarker
Stop
GoSafe

```

Recorder対応機器は追加で以下を持つ。

```text

StopRecording

```

Calibration対応機器は追加で以下を持つ。

```text
ReadCalibration
WriteCalibration
VerifyCalibration
```

## 7. Safety境界

電源・負荷装置はSoftware Cleanupだけに依存しない。

最低限、以下を独立して設計する。

- DUT Enable/IGN/Wakeの安全状態
- Chroma Output OFF / Load OFF
- Setpoint zeroまたは安全値への復帰
- TestStand Abort時Cleanup
- LabVIEW Error時Cleanup
- PC/Application異常時の外部Interlock
- Emergency Stop

既存のCleanup思想は[`../../12_異常系処理とシャットダウン設計.md`](../../12_異常系処理とシャットダウン設計.md)を流用する。
