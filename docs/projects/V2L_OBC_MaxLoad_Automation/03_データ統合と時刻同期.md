# 03. データ統合と時刻同期

**最終整理日:** 2026-09-03  
**State:** Design draft

---

## 1. 目的

本ProjectのData要求は「全部を1個のファイルへ押し込むこと」ではなく、以下を満たすこととする。

1. 1つのTest Runに属するデータを確実に識別できる。
2. 試験条件とDataが分離しない。
3. 機器ごとの時刻軸を後処理で比較・補正できる。
4. 生Data、イベント、判定結果、Version情報を追跡できる。
5. 将来的に単一MF4へ変換/統合できるData Modelを持つ。

---

## 2. 保存単位

`Run ID`を最上位Identityとする。

例:

```text
D:\TestData\2026-09-03\RUN_20260903_000123\
├─ manifest.json
├─ events.csv                 # またはTDMS Event Group
├─ conditions_snapshot.json
├─ teststand_result.*
├─ labview_master.tdms
├─ is8000\
│   └─ <IS8000 recording artifact>
├─ canalyzer\
│   └─ <CAN recording>.mf4
├─ inca\
│   └─ <INCA recording>.mf4
└─ raw_vendor\
    └─ optional vendor files
```

機器ごとに物理ファイルが分かれても、同じ`Run ID`・条件Snapshot・Sync Eventで論理的に1データセットとして扱う。

## 3. Run Manifest

最低限、次を保存する。

```text
Run ID
Test Sequence Name / Version
Test Case ID
Start UTC / End UTC
DUT ID
Operator / Host PC
Result
Abort / Error reason

LabVIEW Version
TestStand Version
Adapter Versions
Instrument Model / Serial / Firmware
CANalyzer Version / Configuration Path
INCA Version / Experiment / Workspace / A2L information
IS8000 Version / Project
RAMScope API / Firmware / Module information

Condition file path + hash
Configuration file path + hash
A2L / HEX / parameter set hash when applicable

```

試験条件Excelを直接参照するだけでなく、Run開始時に使用条件のSnapshotまたはhashを残す。

## 4. Data Sourceごとの推奨保存

| Source | Primary保存 | LabVIEWへ返すData |
|---|---|---|
| Chroma | TDMS event/slow telemetry またはRun Manifest | Setpoint、Readback、Fault、状態 |
| WT5000 | TDMSまたはIS8000 recording | 判定用V/I/P/効率等 |
| MX100 | TDMSまたはIS8000 recording | 判定用温度 |
| Oscilloscope | Vendor waveform file + metadata / 必要ならTDMS変換 | 判定値・artifact path |
| CANalyzer | MF4等のCANalyzer native recording | 判定に必要なSysVar/状態 |
| RAMScope | 既存TDMS、またはIS8000 User Library recording | 判定用RAM値、loss/status |
| INCA/ETK | INCA Recorder MDF/MF4 | 判定用Selected signals / calibration result |
| TestStand | Result/Report | Step Result、判定、Error |

## 5. TDMS → MF4方針

### 5.1 Phase 1

まずRunを壊さず保存できることを優先する。

```text
LabVIEW data     → TDMS
CANalyzer data   → native CAN recording / MF4
INCA data        → MDF/MF4
IS8000 data      → IS8000 recording
                 +
               manifest.json
```

### 5.2 Phase 2

単一MF4が本当に必要な場合のみPost Processを追加する。

要件:

- Channel name collision解決
- Unit / Conversion保持
- Source metadata保持
- Relative/absolute timestamp変換
- Event channel保持
- Signal provenance保持
- Merge前後のsample count検証

元ファイルは削除せず、統合MF4はderived artifactとして扱う。

# 6. 時刻同期の基本原則

Windows上でTestStandから複数機器へSoftware Triggerを順番に送るだけでは、精密な同時開始を保証しない。

したがって同期精度を次の階層で扱う。

```text
Level A  Hardware Trigger / shared clock / IEEE1588等
Level B  Vendor ecosystem内部同期 (IS8000等)
Level C  共通Software Event Marker
Level D  Host command send timestampのみ
```

可能な限りA/Bを採用し、非対応機器はCで後補正できるようにする。Dだけを精密同期の根拠にしない。

## 7. Sync Event

全Systemへ同じ`Sync Event ID`を配布する。

例:

```text
SYNC_000001
SYNC_LOAD_STEP_03
SYNC_CAL_CHANGE_07
```

Master Eventは次の情報を持つ。

```text
Run ID
Sync Event ID
Event Type
Host UTC
Host monotonic tick / QPC
TestStand Step
Requested target systems
Per-system send timestamp
Per-system acknowledgement timestamp
Per-system marker result
Uncertainty / Notes
```

---

## 8. IS8000同期

入手済みControl APIではNotification Streamを利用し、Recording開始/停止成立Eventを受け取れる。

推奨Sequence:

```text
OpenNotificationStream
   ↓
RecStart
   ↓
OnRecordingStarted
   ↓
Host UTC + monotonic tickを記録
   ↓
Run Event Timelineへ追加
```

`RecStart`の送信時刻だけでなく、成立Notification受信時刻も保存する。

**未確定:** Notification自体に機器側絶対timestampが含まれるか、対象Versionでの詳細fieldを実装時にprotoで再確認する。

---

## 9. RAMScope Timestamp

入手済みRAMScope API仕様書 Rev.5.0では、RAM monitor/CAN/Analog packetの`Time`は**測定開始を0とする20 ns周期の64bit count**として記載されている。

したがってRAMScope dataは少なくとも高分解能のrelative timelineを持つ。

絶対時刻へ揃えるには次のいずれかが必要。

- RAMScopeの測定開始絶対時刻API
- Hardware triggerと他DAQの共通Event
- Start/Marker時のHost correlation

既存RAMScope本編でTimestamp解析が更新される場合は、その正本を流用する。

---

## 10. CANalyzer同期

Project PoCで以下を確認する。

1. CANalyzer recordingへEvent/Comment/Markerを挿入できるか。
2. Hardware timestampがMF4へ保持されるか。
3. Measurement Start完了をCOM側で判定できるか。
4. 同一`Sync Event ID`を後解析で検索できる形式で残せるか。

Marker APIが不足する場合は、既存SysVar Writeまたは専用CAN Frame/Event Channelを同期Markerとして使う案を比較する。

---

## 11. INCA同期

INCAはTool API/Recorder側でEvent Comment/Metadataを記録できるかを対象VersionのCHM/Type Libraryで確定する。

目標Sequence:

```text
INCA Recorder Start
   ↓
Write Sync Event ID
   ↓
ETK Measurement
   ↓
Recorder Stop
```

イベントがMDF/MF4内へ残る場合は、CANalyzer/IS8000/TDMSと共通`Sync Event ID`で後処理Alignmentする。

---

## 12. Calibration Event

RAMScope/INCAでオンライン適合を実施した場合は、Data以外に変更Eventを必ず保存する。

```text
Timestamp
Run ID
Test Step
Device
Variable / Address
Before Value
Requested Value
Readback Value
Unit
Result
Error Code
Sync Event ID
```

電力・温度・CAN挙動と適合変更点を同一Timelineで追えるようにする。

---

## 13. Data Quality監視

各DAQは最低限次をRun Manifestまたは専用Quality Channelへ保存する。

- dropped/lost sample count
- buffer overflow
- recorder start/stop result
- communication reconnect count
- timestamp discontinuity
- channel configuration snapshot
- data file size / hash
- sample count

Data fileが存在するだけではRun成功としない。
