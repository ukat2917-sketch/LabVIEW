# 04. VI の仕組み（LabVIEW 基礎）

この章は、LabVIEW を初めて触る人が **次章「[05. VI 設計方針と共通仕様](./05_VI設計方針と共通仕様.md)」を読む前**に
押さえておくべき基礎用語を説明する。05 章以降で出てくる「コネクタペイン」「リファレンス」「入力／出力」
「型定義」「エラー伝搬」といった言葉の意味が分かるようにするのが目的。

> すでに LabVIEW を理解している場合は、この章は飛ばして [05](./05_VI設計方針と共通仕様.md) へ進んでよい。

---

## 4.1 VI とは何か

**VI（Virtual Instrument＝バーチャルインスツルメント）** は、LabVIEW における **1 つのプログラム**
（関数・部品）のこと。拡張子は `.vi`。

- C 言語で言う「関数」、Python で言う「関数／モジュール」に相当する。
- VI は **他の VI から部品として呼び出せる**。呼び出される側の VI を **サブVI（SubVI）** と呼ぶ。
- 本資料の方針「1イベント1VI」とは、**1 つの操作（イベント）を 1 つの VI（部品）にする**という意味。

### VI は 3 つの部分でできている

| 部分 | 役割 | たとえると |
|------|------|-----------|
| **フロントパネル（Front Panel）** | 入力・出力を置く画面（GUI） | 計測器の「操作パネル」 |
| **ブロックダイアグラム（Block Diagram）** | 実際の処理（配線で書く） | パネル裏の「配線・回路」 |
| **アイコン／コネクタペイン** | 他の VI から呼ぶときの「端子」と「見た目」 | IC チップの「ピン配置」 |

LabVIEW は **テキストではなく「配線（ワイヤ）」でプログラムを書く**（グラフィカル言語）。
データはワイヤを通って左から右へ流れる（後述 4.7 データフロー）。

---

## 4.2 フロントパネルと入力・出力（Control / Indicator）

フロントパネルには 2 種類の部品を置く。

| 種類 | 意味 | 役割 | 例 |
|------|------|------|----|
| **制御器（Control）** | **入力** | 外部から VI に値を渡す | 電圧条件、目標電流値、機器リファレンス |
| **表示器（Indicator）** | **出力** | VI から外部へ値を返す | 現在の電流値、実行結果ステータス、エラー情報 |

- **Control＝入力、Indicator＝出力** と覚える。
- ブロックダイアグラム上では、Control は「データの出発点（左側に置く）」、
  Indicator は「データの終着点（右側に置く）」になる。
- 本資料で「入力値」「出力」と書いているものは、この Control / Indicator のこと
  （[05](./05_VI設計方針と共通仕様.md) の入出力仕様）。

---

## 4.3 コネクタペイン と アイコン（VI を部品として呼ぶための「端子」）

VI を **サブVI として他の VI から呼ぶ**には、その VI の「入口・出口」を定義する必要がある。
それが **コネクタペイン（Connector Pane）** と **アイコン（Icon）**。

- **コネクタペイン**：フロントパネル右上にある「ます目」。
  各ます目（端子）に、フロントパネルの Control / Indicator を割り当てる。
  - Control を割り当てた端子 → **入力端子**
  - Indicator を割り当てた端子 → **出力端子**
  - これで「この VI は何を受け取り、何を返すか」が決まる（＝関数の引数と戻り値）。
- **アイコン**：その VI を呼んだとき、ブロックダイアグラム上に表示される小さな絵。

```
   フロントパネル右上            ブロックダイアグラム上のサブVI
   ┌──┬──┐                         ┌─────────┐
   │入力│出力│   ← コネクタペイン     入力 ─▶│  アイコン │─▶ 出力
   ├──┼──┤                         └─────────┘
   │入力│出力│
   └──┴──┘
```

> 重要：**コネクタペインを割り当てていない VI は、TestStand や他の VI から値を渡して呼べない。**
> [05](./05_VI設計方針と共通仕様.md) で「入出力の並びを全 VI で統一する」と言っているのは、
> このコネクタペインの端子配置を揃える、という意味。

## 4.4 リファレンス（Reference / Refnum）とは

**リファレンス**（参照、Refnum）とは、**「開いている機器接続や資源を指し示す“番号札”」** のこと。

- 例：オシロと Ethernet で接続を確立すると、その接続を表す **VISA リファレンス** が得られる。
- 以後、その機器を操作する VI には **リファレンス（番号札）を渡す**ことで「どの機器か」を指定する。
- 機器の実体（接続）は LabVIEW が内部で保持し、VI 間ではこの「番号札」だけを受け渡す。

### なぜリファレンスを引き回すのか

- 機器接続（VISA Open）は **時間がかかる**ので、毎回 Open/Close すると遅く・不安定になる。
- そこで **接続は最初に 1 回だけ開き（[03](./03_LabVIEW環境構築.md) / [11](./11_TestStandシーケンス構築手順.md) の Setup）**、
  得たリファレンスを各操作 VI に渡し回す。最後にまとめて Close する。
- 本資料で各 VI の入出力に「機器リファレンス in / out」があるのはこのため
  （[05](./05_VI設計方針と共通仕様.md) 5.6 / 各 VI の入出力仕様に対応）。

```
[Setup] VISA Open ─▶ Ref ─▶ [電圧設定VI] ─▶ Ref ─▶ [出力ONVI] ─▶ Ref ─▶ [Cleanup] VISA Close
            （同じ番号札を順に渡していく）
```

## 4.5 データ型・クラスタ・型定義（Type Def.）

### よく使うデータ型

| 型 | 用途・例 |
|----|----------|
| 数値（DBL / I32 など） | 電圧値・電流値・モード番号 |
| 文字列（String） | SCPI コマンド、エラーメッセージ |
| ブール（Boolean） | ON/OFF、フラグ |
| 列挙（Enum） | 決まった選択肢（例：ステータス `OK/Warning/Error`） |
| 配列（Array） | 波形データ、複数台のリファレンス |
| **クラスタ（Cluster）** | 複数の値を 1 つに束ねた「構造体」 |

### クラスタ（Cluster）

**クラスタ**は、関連する複数の値を 1 本のワイヤにまとめた **構造体**（C の struct に相当）。
例：「エラー情報」を {機器名・コード・メッセージ・時刻} の 4 項目で 1 つに束ねる。

### 型定義（Type Definition / `.ctl`）

**型定義**とは、Enum やクラスタの「定義（中身の構成）」を **1 ファイル（`.ctl`）として一元管理**する仕組み。

- メリット：**定義を 1 か所直すと、それを使っている全 VI に変更が自動で伝わる。**
  - 例：エラー情報クラスタに「致命度」項目を後から足しても、型定義を直すだけで全 VI に反映される。
- これがないと、項目を増やすたびに全 VI を手で直す羽目になる。
- 本資料で `Status.ctl`（ステータス）や `TestError.ctl`（エラー情報）を**型定義で作る**よう
  推奨しているのはこのため（[05](./05_VI設計方針と共通仕様.md) 5.3 / 5.4）。

## 4.6 エラークラスタとエラー伝搬（error in / error out）

LabVIEW には **標準のエラー処理の仕組み**がある。これを理解すると 05 章の「エラー伝搬」が分かる。

### エラークラスタ

LabVIEW 標準の **エラークラスタ**は次の 3 項目を束ねたクラスタ。

| 項目 | 意味 |
|------|------|
| `status`（Boolean） | エラーが発生したか（True=エラー） |
| `code`（I32） | エラーコード（番号） |
| `source`（String） | どこで発生したか |

### エラー伝搬（エラーチェーン）

ほぼ全ての標準 VI には **`error in`（入力）** と **`error out`（出力）** という端子がある。
これらを **VI から VI へ数珠つなぎに配線**することで、エラーが下流へ流れていく。これを **エラー伝搬**と呼ぶ。

```
[VI-A] error out ─▶ error in [VI-B] error out ─▶ error in [VI-C] ...
```

- **手前でエラーが起きると、後続の VI は処理をスキップして、そのエラーをそのまま下流へ通す**のが定石。
  - 実装：VI 内で `error in` を **Case ストラクチャ**に入れ、「エラー無し」の時だけ実処理を行う。
- こうすると、**どこで最初に失敗したか**が末端まで伝わり、原因を追える。
- 本資料では、この標準エラークラスタ（error in/out）に加えて、機器名などを詳しく入れた
  **`TestError.ctl`（エラー情報）** を別途出力し、TestStand 側で「どの機器で何が起きたか」を
  トレースできるようにする（[05](./05_VI設計方針と共通仕様.md) 5.4 / 5.5）。

## 4.7 データフロー（実行順序の考え方）

LabVIEW は **データフロー**で動く。これは「**入力データが全て揃った VI（ノード）から実行される**」という規則。

- テキスト言語のように「上の行から順に」ではなく、**ワイヤでつながった順（データが流れる順）**に実行される。
- だから **実行順序を決めたいときは、ワイヤでつなぐ**（特に `error in/out` の数珠つなぎが順序の決め手になる）。
- 逆に **ワイヤでつながっていない処理は並列に動ける**。
  これが負荷ランプを別スレッドで並列実行できる理屈につながる（[08](./08_負荷電流VIと並列処理.md)）。

## 4.8 本資料の用語と LabVIEW 用語の対応（早見表）

| 本資料の表現 | LabVIEW の用語 | 一言で |
|--------------|----------------|--------|
| 入力値 | Control（制御器） | VI に渡す値 |
| 出力 | Indicator（表示器） | VI が返す値 |
| 入出力の端子・並び | コネクタペイン | 関数の引数・戻り値の口 |
| 機器リファレンス | VISA Refnum / 参照 | 接続を指す「番号札」 |
| ステータス／エラー情報の定義 | 型定義（Type Def. `.ctl`） | 一元管理する構造体定義 |
| エラーの受け渡し | error in / error out（エラー伝搬） | 失敗を下流へ伝える仕組み |
| 1イベント1VI | SubVI | 操作 1 つ＝部品 1 つ |
| 実行順序 | データフロー | ワイヤが流れる順に実行 |
