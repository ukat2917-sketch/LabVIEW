# 2. ベンダー資料で確定した仕様

## 2.1 `CHINFO_RAM170`は1チャンネル24byte

```c
typedef union CHINFO_RAM170 {
    unsigned long enable;
    unsigned long core;
    unsigned long address;
    unsigned long size;
    unsigned long sign;
    unsigned long speed;
} CHINFO_RAM170;
```

各フィールドは4byteで、1チャンネルは合計24byteとなる。

| offset | フィールド | 型 | 正式定義 |
|---:|---|---|---|
| 0 | `enable` | U32 | `0=無効`、`1=有効` |
| 4 | `core` | U32 | 将来拡張用。現在は`0` |
| 8 | `address` | U32 | 測定対象アドレス |
| 12 | `size` | U32 | `0=1Byte`、`1=2Byte`、`2=4Byte` |
| 16 | `sign` | U32 | `0=unsigned`、`1=signed` |
| 20 | `speed` | U32 | 将来拡張用。現在は`0` |

したがって、次は確定である。

```text
CHINFO Byte Count = 24 × ChNum
```

`Build_CHINFO_170_Raw.vi`は、上表の順序で6個のU32をLittle EndianのU8[4]へ変換し、チャンネル順に連結する。

## 2.2 AddressとSizeの組み合わせ制約

| `size` | 測定サイズ | Address条件 |
|---:|---:|---|
| 0 | 1Byte | 任意のアドレス |
| 1 | 2Byte | 2の倍数 |
| 2 | 4Byte | 4の倍数 |

上位Public VIまたはBuilderで次を検証する。

```text
Size=0
  → Address条件なし

Size=1
  → Address mod 2 == 0

Size=2
  → Address mod 4 == 0
```

不正時のローカルエラー候補：

```text
code = -700113
source = Build_CHINFO_170_Raw.vi: Address alignment is invalid. Channel Index=%d, Address=%d, Size=%d
```

プレースホルダ接続順：

```text
1個目の%d ← Channel Index I32
2個目の%d ← Address U32またはI64へ明示変換した値
3個目の%d ← Size U32またはI32
```

## 2.3 GT17xでは`RAMScopeGT170SetMeasCh`を使用する

GT17x接続時は`RAMScopeGT170SetMeasCh()`の使用が推奨される。

旧`RAMScopeGT150SetMeasCh()`をGT17xのRAMモニタへ使用した場合、測定チャンネルが符号なし固定として扱われる。`sign`を使用する現在の設計では、次を使用する。

```text
Build_CHINFO_170_Raw.vi
  → RS_DLL_GT170SetMeasCh.vi
```

## 2.4 `SYSINFO.module_type`コード

| コード | 正式定義 |
|---:|---|
| `0x00` | RAMモニタ／光RAMモニタ |
| `0x02` | CAN |
| `0x03` | アナログ入力 |
| `0x0E` | 電源通信 |
| `0x0F` | 非接続 |

現在の判定は正しい。

```text
RAM Module? = module_type == I32 x00
CAN Module? = module_type == I32 x02
Connected?  = module_type != I32 x0F
```

## 2.5 `SYSINFO.endian`コード

```text
0 = Big Endian
1 = Little Endian
```

`Endian_RAM`を`RAMScope_Byte_Order.ctl`へ変換するPublic VIでは次を使用する。

```text
Endian_RAM == 0
  → Big Endian

Endian_RAM == 1
  → Little Endian
```

注意：

```text
Parse_SYSINFO_Array.viへ入力するByte Order
```

と、SYSINFOレコード内から読み出した、

```text
Endian_RAMコード
```

は別の値である。前者はSYSINFO構造体自体を解析するためのByte Order、後者は測定データのByte Orderを決めるハードウェア情報である。

## 2.6 Timestampの正式定義

ログデータの1Packetは次の構成である。

```text
Data = ChNum × 4byte
Flag = 4byte
Time = 8byte
```

Timeは、測定開始時を0として20ns周期でカウントアップする64bit値である。

```text
Timestamp Seconds
  = DBL(Timestamp Raw) × DBL 20e-9
```

`20e-9`は作業仮定ではなく、ベンダー資料で確認済みの正式値とする。

単体試験：

```text
Timestamp Raw = 50
50 × 20e-9 = 1e-6 second
```

## 2.7 `0x30100001`の正式定義

```text
0x30100001 = 下位DLL非対応関数
```

現在のハードウェア、下位DLL、API関数の組み合わせに対して、要求した処理が下位DLL側に実装されていない、または対応していない場合に返る。

単純な未接続エラーとして扱わない。

推奨source：

```text
RAMScopeVP API returned 0x30100001: The requested function is not supported by the lower-level DLL. Verify the connected RAMScope model, API function, and DLL combination.
```

## 2.8 モジュール構成設定はPGT版を使用する

旧関数：

```text
RAMScopeGT150SetMdlConfig
```

は使用非推奨である。後継の次を使用する。

```text
RAMScopeGT150PGT_SetMdlConfig
```

呼出順：

```text
RAMScopeGT150GetSysInfo
  → 正常終了を確認
  → RAMScopeGT150PGT_SetMdlConfig
  → SetMeasCond / SetMeasCh / SetLoggingInfo
```

したがって、標準ルートでは`MDLCFG`をLabVIEWで手動生成しない。

```text
採用：RS_DLL_GT150PGT_SetMdlConfig.vi
不採用：MDLCFG Builderを新規作成して通常SetMdlConfigへ渡す構成
```

## 2.9 `ReleaseBufferData`の呼出タイミング

`RAMScopeGT150ReleaseBufferData()`の発行可否は次のとおり。

| 状態 | 発行可否 |
|---|---|
| オフライン | 不可 |
| 測定中 | 不可 |
| アイドル | 可能 |

正しい順序：

```text
MeasStart
  → GetBufferDataを必要回数実行
  → MeasStop
  → アイドル状態
  → ReleaseBufferData
  → DeviceExit
```

`GetBufferData`直後に毎回`ReleaseBufferData`を呼ばない。

LoggingInfo未発行、またはバッファが既に破棄済みの場合でも正常応答を返す仕様のため、Cleanupで呼びやすい。ただし、MeasStopが失敗し測定中の可能性がある場合は、ReleaseBufferDataを呼ばない。

# 4. `RAMScope_Parse_Buffer.vi`改訂手順

## 4.1 Case Structure全体構造

```text
外側error Case Structure
selector = error in.status

├─ Trueケース（既存エラーあり）
│    Packets             = 空のRAMScope_Packet.ctl一次元配列
│    Parsed Packet Count = I32 0
│    Unused Byte Count   = I32 0
│    error out           = 元のerror in
│
└─ Falseケース（既存エラーなし）
     └─ Input Valid? Case Structure
          selector = (ChNum >= 1) AND (DataNum >= 0)

          ├─ Falseケース（入力値不正）
          │    code = -700130
          │
          └─ Trueケース（入力値正常）
               └─ Raw Buffer Sufficient? Case Structure
                    selector = Actual Byte Count >= Expected Byte Count

                    ├─ Falseケース（Raw Buffer不足）
                    │    code = -700131
                    │
                    └─ Trueケース（Raw Buffer十分）
                         └─ DataNum == 0? Case Structure
                              selector = DataNum == 0

                              ├─ Trueケース（DataNum=0）
                              │    空Packetsを正常終了で返す
                              │
                              └─ Falseケース（DataNum>0）
                                   外側ForループでPacket解析
```

## 4.2 外側Falseケース：入力値判定Caseを先に作る

作業領域：

```text
外側error Case Structure
  → Falseケース（error in.status=False：既存エラーなし）
```

この時点ではPacket Sizeをまだ作らない。

1. `Channel List`を配列サイズ（Array Size）へ接続し、I32出力を`ChNum`とする。
2. `Raw Buffer`を別の配列サイズ（Array Size）へ接続し、I32出力を`Actual Byte Count`とする。
3. 以上?（Greater Or Equal?）を2個配置する。
4. 1個目の上側入力へ`ChNum`、下側入力へI32定数`1`を接続する。
5. 2個目の上側入力へ`DataNum`、下側入力へI32定数`0`を接続する。
6. 2個のBooleanをANDへ接続し、`Input Valid?`とする。
7. Input Valid? Case Structureを配置する。
8. `Input Valid?`をselectorへ接続する。

## 4.3 Input Valid? Falseケース（入力値不正）

作業領域：

```text
外側error Case Structure
  → Falseケース
    → Input Valid? Case Structure
      → Falseケース（Input Valid?=False：入力値不正）
```

安全出力：

```text
Packets             = 空のRAMScope_Packet.ctl一次元配列
Parsed Packet Count = I32 0
Unused Byte Count   = I32 0
```

文字列にフォーマット（Format Into String）のFormat String：

```text
RAMScope_Parse_Buffer.vi: ChNum must be >= 1 and DataNum must be >= 0. ChNum=%d, DataNum=%d
```

接続：

```text
1個目の%d ← ChNum I32
2個目の%d ← DataNum I32
```

名前でバンドル（Bundle By Name）：

```text
基準クラスタ ← 外側Falseケースへ入った正常なerror in
status       ← Boolean True
code         ← I32 -700130
source       ← Format Into String出力
```

## 4.4 Input Valid? Trueケース：Packet Sizeを作る

作業領域：

```text
外側error Case Structure
  → Falseケース
    → Input Valid? Case Structure
      → Trueケース（Input Valid?=True：入力値正常）
```

1. 乗算（Multiply）の上側入力へ`ChNum`、下側入力へI32定数`4`を接続する。
2. 乗算出力を`Channel Data Size`とする。
3. 加算（Add）の上側入力へ`Channel Data Size`、下側入力へI32定数`12`を接続する。
4. 加算出力を`Packet Size`とする。
5. 2個目の乗算の上側入力へ`Packet Size`、下側入力へ`DataNum`を接続する。
6. 出力を`Expected Byte Count`とする。
7. 減算（Subtract）の上側入力へ`Actual Byte Count`、下側入力へ`Expected Byte Count`を接続する。
8. 出力を`Calculated Unused Byte Count`とする。
9. 以上?（Greater Or Equal?）の上側入力へ`Actual Byte Count`、下側入力へ`Expected Byte Count`を接続する。
10. Boolean出力を`Raw Buffer Sufficient?`とする。
11. Raw Buffer Sufficient? Case Structureを配置する。
12. `Raw Buffer Sufficient?`をselectorへ接続する。

式：

```text
Packet Size = ChNum × 4 + 12
Expected Byte Count = Packet Size × DataNum
Calculated Unused Byte Count = Actual Byte Count - Expected Byte Count
```

評価例：

```text
ChNum = 2
DataNum = 1
Actual Byte Count = 20
Packet Size = 2 × 4 + 12 = 20
Expected Byte Count = 20 × 1 = 20
20 >= 20 → True
```

したがって、Trueケース（Raw Buffer十分）へ進む。

## 4.5 Raw Buffer Sufficient? Falseケース（Raw Buffer不足）

作業領域：

```text
外側error Case Structure
  → Falseケース
    → Input Valid? Trueケース
      → Raw Buffer Sufficient? Falseケース
```

安全出力：

```text
Packets             = 空のRAMScope_Packet.ctl一次元配列
Parsed Packet Count = I32 0
Unused Byte Count   = I32 0
```

Format String：

```text
RAMScope_Parse_Buffer.vi: Raw Buffer is too small. Expected=%d, Actual=%d
```

接続：

```text
1個目の%d ← Expected Byte Count I32
2個目の%d ← Actual Byte Count I32
```

Bundle By Name：

```text
基準クラスタ ← 前段の正常error cluster
status       ← Boolean True
code         ← I32 -700131
source       ← Format Into String出力
```

`-700130`用のsource文字列を流用しない。

## 4.6 Raw Buffer Sufficient? Trueケース：DataNum判定を作る

作業領域：

```text
外側error Case Structure
  → Falseケース
    → Input Valid? Trueケース
      → Raw Buffer Sufficient? Trueケース
```

1. 等しい?（Equal?）の上側入力へ`DataNum`、下側入力へI32定数`0`を接続する。
2. 出力を`DataNum == 0?`とする。
3. DataNum == 0? Case Structureを配置する。
4. `DataNum == 0?`をselectorへ接続する。

### Trueケース（DataNum=0）

```text
Packets             = 空のRAMScope_Packet.ctl一次元配列
Parsed Packet Count = I32 0
Unused Byte Count   = Calculated Unused Byte Count
error out           = 正常error cluster
```

### Falseケース（DataNum>0）

外側Forループを配置し、N端子へ`DataNum`を接続する。

## 4.7 外側Forループ：Packet単位

作業領域：

```text
外側error False
  → Input Valid? True
    → Raw Buffer Sufficient? True
      → DataNum == 0? False
        → 外側Forループ
```

1. error用シフトレジスタを追加する。
2. 左外側端子へ前段の正常error clusterを接続する。
3. 外側Forループの反復端子`i`を`Packet Index`として扱う。
4. `Packet Index × Packet Size`を`Packet Start`とする。
5. error左内側の`status`をPacket Error? Case Structureのselectorへ接続する。

### Trueケース（packet error.status=True：既存エラーあり）

```text
Packet単体クラスタ = デフォルトRAMScope_Packet.ctl
Append Packet?      = Boolean False
error次値           = error左内側
```

### Falseケース（packet error.status=False：現在Packetを解析）

内側Forループ、Flag、Timestamp、Packetクラスタ生成を配置する。

## 4.8 内側Forループ：Channel単位

LabVIEW画面上では外側も内側も反復端子は`i`と表示される。

```text
外側Forループのi = Packet Index
内側Forループのi = Channel Index
```

資料中の`j`は内側Forループのiを意味する。

1. `Channel List`を内側Forループ左枠へ接続する。
2. 入力トンネルの自動指標付けを有効にする。
3. N端子は未配線にする。
4. error用シフトレジスタを追加する。
5. 外側error左内側を内側error左外側へ接続する。
6. `Value Start = Packet Start + Channel Index × 4`を作る。
7. Raw Bufferの`Value Start`からlength=I32 `4`を部分配列で切り出す。
8. U8[4]を`U8x4_To_U32.vi`へ接続する。
9. ChannelクラスタからName、Address、Sign、Scale、Offset、Unitを取り出す。
10. Raw U32をDBLへ変換し、符号なし値を作る。
11. Raw U32を型変換（Type Cast）でI32として解釈し、DBLへ変換して符号あり値を作る。
12. `Sign == 0`を選択（Select）のselectorへ接続する。
13. True入力へ符号なしDBL、False入力へ符号ありDBLを接続する。
14. 選択出力を`Value`とする。
15. `Engineering Value = Value × Scale + Offset`を計算する。
16. `RAMScope_Channel_Value.ctl`を名前でバンドルする。
17. `Channel Index`へ内側Forループのiを接続する。
18. Channel Value単体クラスタを右枠へ接続し、自動指標付けでChannel Values配列を作る。
19. 変換SubVIのerror outを内側error右内側へ接続する。

## 4.9 FlagとTimestampの作業領域

FlagとTimestampは1Packetにつき1個であるため、内側Forループへ入れない。

作業領域：

```text
外側Forループ内
  → Packet Error? Falseケース内
    → 内側Forループの外側
```

1. `Flag Start = Packet Start + ChNum × 4`を作る。
2. Raw Bufferから`Flag Start`、length=I32 `4`を切り出す。
3. U8[4]を`U8x4_To_U32.vi`へ接続し、出力を`Flag`とする。
4. `Timestamp Start = Flag Start + I32 4`を作る。
5. Raw Bufferから`Timestamp Start`、length=I32 `8`を切り出す。
6. U8[8]を`U8x8_To_U64.vi`へ接続し、出力を`Timestamp Raw`とする。
7. Timestamp RawをDBLへ変換する。
8. DBL定数`20e-9`と乗算し、`Timestamp Seconds`とする。

error接続：

```text
内側Forループerror右外側
  → Flag変換VI error in
  → Flag変換VI error out
  → Timestamp変換VI error in
  → Timestamp変換VI error out
  → 外側Forループerror右内側
```

## 4.10 Packetクラスタと条件付き指標付け

Packet Error? Falseケース内で、`RAMScope_Packet.ctl`単体クラスタを名前でバンドルする。

```text
Packet Index      ← 外側Forループのi
Channel Values    ← 内側Forループの自動指標付け出力
Flag              ← Flag変換結果
Timestamp Raw     ← Timestamp変換結果
Timestamp Seconds ← 20e-9乗算結果
```

Packet単体クラスタを外側Forループ右枠へ接続する。

Timestamp変換後の最終error clusterから`status`を取り出す。

```text
最終error.status
  → NOT
  → Append Packet?
```

外側ForループのPacket出力トンネルを条件付き指標付けへ変更する。

```text
Packet単体クラスタ → 条件付き出力トンネル
Append Packet?      → 条件端子
```

正常時だけPacketが配列へ追加される。

```text
最終error.status=False
  → NOT=True
  → Append Packet?=True
  → PacketをPackets配列へ追加
```

Packet Error? TrueケースではAppend Packet?をFalseにし、デフォルトPacketを配列へ追加しない。

## 4.11 Parsed Packet CountとUnused Byte Count

外側Forループ後のPackets配列を分岐する。

```text
Packets配列
  ├─ DataNum判定CaseのPackets出力トンネル
  └─ 配列サイズ（Array Size）
       → Parsed Packet Count
```

`Parsed Packet Count`をForループのN端子や最終iから作らない。

`Unused Byte Count`はForループへ接続しない。

```text
Calculated Unused Byte Count
  = Actual Byte Count - Expected Byte Count
```

を、DataNum判定Falseケースの出力トンネルへ直接接続する。

## 4.12 Packetsの型

`RAMScope_Packet.ctl`をフロントパネルへ直接ドラッグすると単体クラスタになる。

最終出力`Packets`は次の型である。

```text
RAMScope_Packet.ctl一次元配列
```

作成方法：

```text
外側Forループ後のPackets配列ワイヤを右クリック
  → 作成
  → 表示器
```

または、空の配列枠へ`RAMScope_Packet.ctl`を入れる。

Caseごとに要素数が異なることは問題ない。

```text
エラー時 = 0要素
正常時   = 解析成功Packet数
```

型が同じ一次元配列であることが条件である。

# 5. `RAMScope_Parse_Buffer.vi`単体試験結果

## 5.1 入力

Channel List：2要素。

```text
Channel 0
  Name   = Unsigned
  Sign   = 0
  Scale  = 1
  Offset = 0

Channel 1
  Name   = Signed
  Sign   = 1
  Scale  = 1
  Offset = 0
```

```text
DataNum = 1
Byte Order = Little Endian
```

Raw BufferはU8[20]。

```text
index  0..3  = x01 x00 x00 x00
index  4..7  = xFE xFF xFF xFF
index  8..11 = xA5 x00 x00 x00
index 12..19 = x32 x00 x00 x00 x00 x00 x00 x00
```

## 5.2 実測合格結果

```text
Parsed Packet Count = 1
Unused Byte Count   = 0

Packets[0].Packet Index = 0

Channel Values[0]
  Channel Index     = 0
  Name              = Unsigned
  Raw U32           = 1
  Value             = 1
  Engineering Value = 1
```

# 6. データ保存を追加する理由

現在の構成には次が存在する。

```text
Build_LOGINFO_Raw.vi
  → RS_DLL_GT150SetLoggingInfo.vi
```

これはRAMScopeVP APIへ、ログデバイス、ログサイズ、バッファサイズ等を設定する処理である。

一方、TestStandのレポート、後解析、証跡として使用できるように、LabVIEWが解析した`Packets`を明示的にファイルへ保存する処理は別途必要である。

次の2系統を区別する。

```text
A. RAMScope側のロギング／バッファ設定
   Build_LOGINFO_Raw.vi
   → RS_DLL_GT150SetLoggingInfo.vi

B. LabVIEW側の測定結果保存
   RAMScope_File_Log_Open.vi
   → RAMScope_File_Log_Append.vi
   → RAMScope_File_Log_Close.vi
```

Aを実装しただけで、解析済み測定値のTDMSまたはCSVが生成されると扱わない。

# 7. ファイルロギングの採用構成

## 7.1 保存形式

本番形式はTDMSを採用する。

理由：

- LabVIEW標準機能で追記できる。
- 数値型を保持できる。
- 長時間・多チャンネル測定でCSVより書込負荷を抑えやすい。
- メタデータをプロパティとして保存できる。

CSVは任意のエクスポート機能とし、測定ループの本番保存には使用しない。

## 7.2 追加フォルダとVI

```text
30_RAMScope\
├─ 00_Common\
│  ├─ RAMScope_File_Log_Config.ctl
│  └─ RAMScope_File_Log_State.ctl
│
├─ 25_File_Logging\
│  ├─ RAMScope_File_Log_Open.vi
│  ├─ RAMScope_File_Log_Append.vi
│  ├─ RAMScope_File_Log_Close.vi
│  └─ RAMScope_File_Log_Write_Metadata.vi
│
└─ 30_Public\
   └─ RAMScope_Acquire_And_Log.vi
```

## 7.3 `RAMScope_File_Log_Config.ctl`

| フィールド | 型 | 用途 |
|---|---|---|
| `Enable` | Boolean | Falseならファイル保存を行わない |
| `Output Directory` | Path | 保存フォルダ |
| `Base File Name` | String | 拡張子を除く基本名 |
| `Create Unique Name?` | Boolean | 同名時に日時等を付与する |
| `Overwrite?` | Boolean | Trueの場合のみ既存ファイル上書きを許可 |
| `Flush Every Read?` | Boolean | 各Read後にFlushするか |
| `Save Raw U32?` | Boolean | Raw U32を保存する |
| `Save Value?` | Boolean | 符号処理後Valueを保存する |
| `Save Engineering Value?` | Boolean | Scale／Offset適用値を保存する |
| `Save Raw Buffer?` | Boolean | 生U8配列を別Groupへ保存するか |

`Create Unique Name?=True`を本番既定値とする。`Overwrite?=False`を本番既定値とする。

## 7.4 TDMSファイル構造

### Root Properties

```text
Start Time
UnitNo
kind
MdlNo_RAM
Endian_RAM
Channel Count
Byte Order
RAMScopeVP API Version（取得できる場合）
Test Name
Serial Number / DUT ID（TestStandから渡す場合）
```

### Group `Packets`

| Channel名 | 型 | 内容 |
|---|---|---|
| `Packet Index` | I32またはI64 | Packet番号 |
| `Timestamp Raw` | U64 | 20nsカウント値 |
| `Timestamp Seconds` | DBL | 測定開始からの秒 |
| `Flag` | U32 | RAMScopeステータスフラグ |

各RAMチャンネルは、Channel IndexとNameを組み合わせて重複しない名称を作る。

```text
CH000_Unsigned_RawU32
CH000_Unsigned_Value
CH000_Unsigned_Engineering
CH001_Signed_RawU32
CH001_Signed_Value
CH001_Signed_Engineering
```

NameにTDMSで扱いにくい文字がある場合は、File Logger内部で置換する。表示名はChannel Propertyへ元文字列を保存する。

### Group `ReadStatus`

1回の`RAMScope_Read.vi`につき1レコードを保存する。

```text
Read Index
Read Time
DataNum
Parsed Packet Count
LostDataNum
Unused Byte Count
Read Error Code
```

Raw Bufferを保存する場合は、別Group `RawBuffer`へRead単位で保存する。

# 8. File Logger VI作成手順

## 8.1 `RAMScope_File_Log_Open.vi`

### 0. 目的

測定開始前にTDMSファイルを生成し、Root PropertiesとChannel Propertiesを書き込み、後段へLog Stateを返す。

### 1. 入出力

| 端子 | 方向 | 型 |
|---|---|---|
| `Log Config` | 入力 | `RAMScope_File_Log_Config.ctl` |
| `UnitNo` | 入力 | I32 |
| `kind` | 入力 | I32 |
| `MdlNo_RAM` | 入力 | I32 |
| `Endian_RAM` | 入力 | I32 |
| `Channel List` | 入力 | `RAMScope_Channel.ctl`一次元配列 |
| `Test Metadata` | 入力 | Stringまたは専用cluster |
| `error in` | 入力 | error cluster |
| `Log State` | 出力 | `RAMScope_File_Log_State.ctl` |
| `Actual File Path` | 出力 | Path |
| `error out` | 出力 | error cluster |

### 2. Case Structure

```text
外側error Case Structure
selector = error in.status

Trueケース（既存エラーあり）
  → Openを行わない
  → Log State.Valid? = False
  → 元errorを返す

Falseケース（既存エラーなし）
  → Log Config.Enable? Case Structure
```

```text
Enable=Falseケース
  → ファイルを作らない
  → Log State.Valid? = False
  → 正常終了

Enable=Trueケース
  → 保存フォルダ確認
  → ファイル名生成
  → TDMS Open
  → Metadata書込
  → Log State.Valid? = True
```

### 3. ファイル名規則

推奨：

```text
<Base File Name>_yyyyMMdd_HHmmssfff.tdms
```

例：

```text
RAMScope_EngineTest_20260717_163045123.tdms
```

フォルダが存在しない場合は、フォルダ作成（Create Folder）を使用する。作成失敗時は測定を開始しない。

## 8.2 `RAMScope_File_Log_Append.vi`

### 0. 目的

1回のReadで取得したPacketsとRead状態を、既存TDMSへ追記する。

### 1. 入出力

```text
入力：Log State、Packets、DataNum、LostDataNum、Unused Byte Count、Raw Buffer、error in
出力：Updated Log State、Written Packet Count、error out
```

### 2. 作業順

1. 外側error Case Structureを配置する。
2. `error in.status`をselectorへ接続する。
3. Trueケース（既存エラーあり）では測定値を追記せず、Log Stateをそのまま返す。
4. Falseケース（既存エラーなし）に`Log State.Valid?` Case Structureを配置する。
5. Falseケース（Logger無効）では何も書かず正常終了する。
6. Trueケース（Logger有効）で`Array Size(Packets)`を取得する。
7. Packet数が0ならReadStatusだけを保存する。
8. Packet数が1以上ならPacket配列をチャンネル別一次元配列へ展開する。
9. TDMS Writeで`Packets` Groupへ追記する。
10. `ReadStatus` GroupへRead単位の値を1サンプル追記する。
11. `Flush Every Read?=True`の場合だけTDMS Flushを実行する。
12. 実際に書き込んだPacket数を`Written Packet Count`へ返す。

### 3. Packetsの展開

外側ForループでPacketsを1要素ずつ処理する。

```text
Packet Index配列
Timestamp Raw配列
Timestamp Seconds配列
Flag配列
```

を生成する。

Channel Valuesはチャンネル数が固定であることを前提に、Channel Indexごとの配列へ転置する。

チャンネル数が途中で変化した場合は、ファイル構造が変わるためエラーとする。

推奨エラー：

```text
code = -700160
source = RAMScope_File_Log_Append.vi: Channel count changed during logging. Expected=%d, Actual=%d
```

## 8.3 `RAMScope_File_Log_Close.vi`

### 0. 目的

前段エラーが存在してもTDMS FlushとCloseを試み、ファイル参照を解放する。

### 1. Cleanupルール

通常VIの外側エラーガードとは異なり、Closeは`error in.status=True`でも実行を試みる。

```text
Log State.Valid?=True
  → TDMS Flush
  → TDMS Close
  → Log State.Valid?=False
```

元エラーがある場合は元エラーを主エラーとして保持し、Closeエラー情報をsource末尾へ追加する。

元エラーがなくCloseだけ失敗した場合は、Closeエラーを返す。

Close後のLog Stateは必ず無効状態を返す。

# 9. 本番用LabVIEW構成（TestStandなし）

## 9.1 `RAMScope_Acquire_And_Log.vi`

本番用トップVIは、機器制御、測定ループ、ファイル保存、Cleanupを統合する。ただしDLL、Parser、File Loggerの内部処理は各SubVIへ分離する。

### 9.1.1 入力

```text
Meas Config
Channel List
Module Log Configs
File Log Config
Stop Request
Read Interval ms
Test Metadata
error in
```

### 9.1.2 出力

```text
Actual File Path
Total Parsed Packet Count
Total LostDataNum
Last Timestamp Seconds
Status
TestError
error out
```

### 9.1.3 正常シーケンス

```text
RAMScope_Connect.vi
  → RAMScope_Init.vi
  → RAMScope_Set_Cond.vi
  → RAMScope_File_Log_Open.vi
  → RAMScope_Log_Start.vi
  → While Loop
       RAMScope_Read.vi
         → RAMScope_File_Log_Append.vi
         → Total Count更新
         → Stop条件判定
         → Wait (ms)
  → RAMScope_Log_Stop.vi
  → RAMScope_Release.vi
  → RAMScope_File_Log_Close.vi
  → RAMScope_Close.vi
```

File Log Openが失敗した場合はMeasStartを実行しない。

File Log Appendが失敗した場合は、停止要求をTrueにして測定ループを終了し、Cleanupへ進む。

### 9.1.4 Cleanup順序

```text
測定開始済み?
  → Yes：RAMScope_Log_Stop.vi

MeasStop成功またはアイドル確認済み?
  → Yes：RAMScope_Release.vi
  → No ：ReleaseBufferDataを呼ばない

RAMScope_File_Log_Close.vi
RAMScope_Close.vi
```

ファイルCloseはRAMScope側のStopやReleaseが失敗しても必ず試みる。
