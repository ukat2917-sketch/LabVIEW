# 09. RAMScope（GT170）実装方針

RAMScope（GT170、CAM モジュール付）で **RAM の計測** と **CAN 操作** を LabVIEW から行うための
実装方式を比較・選定する。

## 9.1 実装方式の候補

### 方式1：RAMScope の API を呼び出す
- **メリット**：費用がかからない（既存 API を使う）。
- **デメリット**：**DLL の解読が大変**（関数仕様の把握、引数・戻り値の型解析が必要）。
- LabVIEW からは **Call Library Function Node（CLFN）** で DLL を呼び出す。
  - DLL のエクスポート関数・ヘッダ（関数プロトタイプ）・型定義の入手が前提。
  - → DLL を読み解き、本実装が可能かを検証する（Claude Code での実装可否も含め確認）。

### 方式2：マックシステムズのドライバを使用する
- **メリット**：RAMScope の機能を **簡単に LabVIEW で利用** できる（一番早い）。
- **デメリット**：**費用が高額の可能性**。**CAN 操作が可能かは要確認**。

## 9.2 比較表

| 観点 | 方式1：API(DLL) 直叩き | 方式2：マックシステムズ製ドライバ |
|------|------------------------|-----------------------------------|
| 費用 | かからない | 高額の可能性 |
| 実装難易度 | 高（DLL 解読） | 低（提供 VI を使う） |
| 開発期間 | 長い | 短い（最速） |
| RAM 計測 | 可（仕様解読次第） | 可 |
| CAN 操作 | 可（API にあれば） | **要確認** |
| 保守性 | 自前依存 | ベンダ依存 |

## 9.3 選定の進め方（推奨）

1. **まず情報収集**
   - マックシステムズ製ドライバの **価格・対応機能（特に CAN 操作可否）・対応 LabVIEW バージョン** を確認。
   - RAMScope API（DLL）の **関数仕様書／ヘッダの入手可否** を確認。
2. **判断基準**
   - ドライバで CAN 操作まで賄え、費用が許容範囲 → **方式2（最速・確実）**。
   - 費用を抑えたい／DLL 仕様が入手でき解読可能 → **方式1**。
3. **方式1を採る場合の検証**
   - DLL のエクスポート関数を確認（依存関係ツール等）。
   - 1 関数（例：初期化・1 変数読み出し）を CLFN で呼べることを PoC で実証。
   - 呼べれば、本資料の VI 群（`RAMScope_Init/Log_Start/Read/Stop/Reset`）を実装。

## 9.4 Call Library Function Node（CLFN）実装の要点（方式1）

1. ブロックダイアグラムに **CLFN** を配置。
2. DLL パス・呼び出し規約（`stdcall`/`cdecl`）・関数名を設定。
3. 引数（型・受け渡し：値/ポインタ/配列）を関数プロトタイプどおりに設定。
4. RAM アドレス／変数名の指定、計測開始・停止・値読み出しの各関数をラップして VI 化。
5. エラーコードを `TestError.ctl` に変換して出力。

> 文字列・構造体・ポインタ引数は型・メモリ管理の扱いに注意（解読の主な難所）。

## 9.5 異常系での扱い（重要）

- RAMScope はエラー発生時、**一番最後にリセット**する。
- 順序：**DUT の電源を落としてから、RAMScope を落とす（リセット）**。
- `RAMScope_Reset.vi` を Cleanup の最後段に配置する（[11](./11_異常系処理とシャットダウン設計.md)）。

## 9.6 未確定事項（要決定）

- 方式1 / 方式2 のどちらを採用するか。
- 方式2 の費用、CAN 操作対応可否。
- 方式1 の DLL 仕様入手可否・解読可否（PoC 必須）。
