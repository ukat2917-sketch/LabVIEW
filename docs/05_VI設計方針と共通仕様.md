# 05. VI 設計方針と共通仕様

> **前提知識**：VI、コネクタペイン、型定義、error clusterが不明な場合は、先に [04](./04_VIの仕組み_LabVIEW基礎.md) を読む。

## 5.1 1イベント1VI

試験フロー上の1つの操作を1つのVIへ分離する。

| イベント | VI名例 |
|----------|--------|
| RAMScope接続 | `RAMScope_Connect.vi` |
| RAMScope初期化 | `RAMScope_Init.vi` |
| RAMScope計測開始 | `RAMScope_Log_Start.vi` |
| RAMScopeデータ取得 | `RAMScope_Read.vi` |
| RAMScope計測停止 | `RAMScope_Log_Stop.vi` |
| RAMScope終了 | `RAMScope_Close.vi` |
| オシロ計測開始 | `DLM5058_Acquire_Start.vi` |
| オシロ波形保存 | `DLM5058_Save_Waveform.vi` |
| 温度ロガー計測開始 | `MX100_Log_Start.vi` |
| 高圧電源設定 | `RZX_Voltage_Set.vi` |
| 低圧電源設定 | `PPX_Voltage_Set.vi` |
| CANモード送信 | `CAN_Send_Mode.vi` |

命名規則：

```text
<機器または対象>_<動作>.vi
```

### 目的

- TestStandでステップの並び替えができる
- 1つの機能変更が他機能へ波及しにくい
- 単体テストしやすい
- 別試験へ流用しやすい

## 5.2 VIへ持たせる共通端子

### 入力

| 端子 | 型 | 用途 |
|------|----|------|
| `error in` | 標準error cluster | 前段エラーの受け取り |
| 試験条件 | 数値、Enum、配列、クラスタ | TestStandから渡す条件 |
| 機器リファレンスin | VISA / セッション参照 | **リファレンス型APIを使用する機器だけ** |

### 出力

| 端子 | 型 | 用途 |
|------|----|------|
| `error out` | 標準error cluster | 後段VIとTestStandへの伝播 |
| `実行結果ステータス` | `Status.ctl` | OK / Warning / Error / Timeout |
| `エラー情報` | `TestError.ctl` | 機器名、コード、メッセージ、時刻、致命度 |
| 計測値 | 数値、配列、クラスタ | ログ・判定用 |
| 機器リファレンスout | VISA / セッション参照 | リファレンス型APIを使用する機器だけ |

### RAMScopeの例外

RAMScopeVP APIは`DeviceInit`でセッションハンドルを返さず、DLL内部で状態を管理する。そのためRAMScope VIにVISAリファレンスin/outは持たせない。

RAMScope VI間で必要に応じて渡す値：

- `MdlNo_RAM`
- `MdlNo_CAN`
- `Endian_RAM`
- チャンネル数
- 標準error cluster

## 5.3 待ち時間とフロー制御

- VI内部へ試験都合の`Wait(ms)`を入れない。
- 待ち、繰り返し、条件分岐、リトライはTestStandで管理する。
- VIは「呼ばれた処理を行い、結果を返す」ことに集中する。
- 負荷ランプのように機能自体が時間変化を持つ場合のみ、VI内部に時間制御を持たせる。
- `RAMScope_Read.vi`のポーリング周期はTestStand側で管理する。

## 5.4 `Status.ctl`

実行結果ステータスはEnum型定義として共通化する。

| 値 | 意味 | TestStandの扱い |
|----|------|------------------|
| `OK` | 正常完了 | 次ステップへ進む |
| `Warning` | 継続可能な注意 | 記録して継続 |
| `Error` | 異常 | Mainを中断しCleanupへ |
| `Timeout` | 応答タイムアウト | 原則Error扱い |

## 5.5 `TestError.ctl`

| 項目 | 推奨型 | 説明 |
|------|--------|------|
| `機器名` | String | `RAMScope`、`DLM5058`等 |
| `エラーコード` | **U32** | RAMScopeの16進コードをビット列どおり保持するため |
| `エラーメッセージ` | String | 人が読める説明 |
| `発生時刻` | Timestamp | エラー発生時刻 |
| `致命度` | EnumまたはBoolean | Cleanup、中断、継続の判断 |

SCPIの負数コードを同じU32へ格納する場合は、メッセージ内に符号付き値も記録する。機器ごとにコード体系が異なるため、数値だけでなく機器名とメッセージを必ずセットで残す。

## 5.6 標準error clusterの伝播

通常VIは次の構成とする。

```text
error in
  → Case Structure
      ├─ errorあり：実処理をスキップして元エラーを出力
      └─ errorなし：機器操作を実行
  → error out
```

- 前段エラーを勝手に消さない。
- 機器固有エラーは標準error clusterへ変換する。
- `Error_To_TestStatus.vi`で`Status.ctl`と`TestError.ctl`へ変換する。
- Cleanup専用VIは、前段エラーがあっても終了処理を試み、元エラーとCleanupエラーを`Merge Errors`で統合する。

## 5.7 RAMScopeの2系統エラー

RAMScopeのCLFNでは次を分ける。

| 経路 | 内容 |
|------|------|
| CLFNの`error out` | DLL未検出、関数未検出、呼び出し設定等のLabVIEW側エラー |
| APIのReturnCode | デバイス未接続、状態不正、引数不正等のRAMScope側結果 |

```text
CLFN ReturnCode
  → RAMScope_Code_To_Error.vi
  → Error_To_TestStatus.vi
  → Status.ctl / TestError.ctl / error out
```

`error out`が正常でもReturnCodeが異常になることはあり得る。両方を必ず評価する。

## 5.8 接続と終了

### VISA機器

```text
Setup  : Openしてリファレンスを保持
Main   : 各VIへリファレンスを渡す
Cleanup: Close
```

### RAMScope

```text
Setup  : Connect → Init → Config → Set_Cond
Main   : Start → Read / Parse → Stop → Release候補
Cleanup: Close（DeviceExit）
```

`RAMScope_Close.vi`はCleanupで必ず実行し、前段エラーがあってもDeviceExitを試みる。
